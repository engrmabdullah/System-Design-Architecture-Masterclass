المفهوم 01

Coupling — الارتباط

الكلمة اللي كل حاجة تانية في الموديول بتشتق منها.

Coupling الارتباط بين الوحدات
التعريف الدقيق قد إيه وحدة كود بتعتمد على تفاصيل وحدة تانية. المقياس العملي: «لو غيّرت في B، هل مضطر أفتح A وأعدّلها؟»
لو الإجابة أيوة ⇒ A مرتبطة بـ B ارتباط عالي.
تشبيه 🔌 الأجهزة في بيتك مرتبطة بالكهربا عن طريق فيشة موحّدة. لو غيّرت شركة الكهربا أو حطيت ألواح شمسية — الغسالة ما بتتغيّرش.
قارن ده بجهاز ملحوم مباشرة في السلك: أي تغيير في المصدر = تفكيك الجهاز.
الفيشة = الـ Interface. ده كل الموضوع باختصار.
تطبيق .NET كل new بتكتبها جوّه كلاس على نوع ملموس = ارتباط. وDependency Injection في ASP.NET Core موجود أصلاً عشان يشيل الـ new دي من جوّه الكلاسات ويحطها في مكان واحد (Program.cs).
فخ شائع ⚠️ الناس بتفتكر إن الهدف صفر ارتباط — وده مستحيل ومش مطلوب. نظام من غير ارتباط خالص = وحدات ما بتكلّمش بعضها = مش نظام.
الهدف الحقيقي: خلّي الارتباط على عقود ثابتة بدل ما يكون على تفاصيل متغيّرة.
إزاي تقيسه في مشروعك النهاردة افتح آخر 10 Pull Requests واحسب متوسط عدد الملفات اللي اتغيّرت في كل واحد. لو المتوسط فوق 8–10 ملفات لميزة صغيرة ⇒ عندك ارتباط عالي، مش «شغل كتير».
OrderService.csC# / .NET 9
// ══════════ ❌ ارتباط عالي (High Coupling) ══════════
public class OrderService
{
    public async Task PlaceAsync(Order order)
    {
        // الكلاس ده عارف: نوع الداتابيز، ونص الـ SQL، وسيرفر الإيميل، وبورت الـ SMTP
        using var conn = new SqlConnection("Server=.;Database=Shop;...");
        await conn.ExecuteAsync("INSERT INTO Orders ...", order);

        using var smtp = new SmtpClient("smtp.mail.com", 587);
        smtp.Credentials = new NetworkCredential("shop@x.com", "P@ssw0rd");
        await smtp.SendMailAsync(new MailMessage(...));

        await new HttpClient().PostAsJsonAsync("https://erp.local/sync", order);
    }
}
// عدد أسباب التغيير هنا = 4  (قاعدة بيانات · إيميل · ERP · قواعد الطلب نفسها)
// ومستحيل تختبرها من غير SQL Server حقيقي وسيرفر إيميل حقيقي.

// ══════════ ✅ ارتباط منخفض (Low Coupling) ══════════
public class OrderService(
    IOrderRepository orders,
    INotificationSender notifier,
    IErpGateway erp)                // Primary Constructor — C# 12+
{
    public async Task PlaceAsync(Order order, CancellationToken ct)
    {
        await orders.AddAsync(order, ct);      // مش عارف SQL ولا Mongo
        await notifier.NotifyAsync(order, ct);  // مش عارف إيميل ولا SMS
        await erp.PushAsync(order, ct);         // مش عارف HTTP ولا Queue
    }
}
// عدد أسباب التغيير = 1  (قواعد الطلب بس)
الكود ده بيقول إيه سطر سطر؟ في النسخة الأولى، OrderService بتعمل new على SqlConnection وSmtpClient وHttpClient — يعني بتعرف تفاصيل تنفيذ ثلاث تقنيات مختلفة، وكمان بتحمل نصوص اتصال وباسوردات.
في النسخة التانية، هي بتستقبل ثلاث واجهات عن طريق الـ Constructor. هي عارفة إن فيه حاجة اسمها «مخزن طلبات» بتعمل AddAsync — بس مش عارفة ولا مهتمة إن التنفيذ ده SQL Server ولا ملف على الديسك ولا قائمة في الذاكرة وقت الاختبار.
النتيجة العملية: النسخة التانية بتتختبر في 5ms من غير أي بنية تحتية، والأولى محتاجة بيئة كاملة وبتاخد ثواني.

المفهوم 02

Cohesion — التماسك

التوأم التاني. الارتباط بيتكلم عن بين الوحدات، والتماسك بيتكلم عن جوّه الوحدة.

Cohesion التماسك الداخلي
التعريف الدقيق قد إيه الحاجات اللي جوّه الوحدة الواحدة بتخدم نفس الغرض. الاختبار: «لو وصفت الكلاس ده في جملة واحدة من غير كلمة "و" — هينفع؟»
لو قلت «بيحسب الضريبة و بيبعت إيميل و بيصدّر Excel» ⇒ تماسك ضعيف.
تشبيه 🧰 دولاب المطبخ فيه أدوات المطبخ بس. لما تلاقي فيه مفك ومسامير وشاحن موبايل — الدولاب ده بقى «درج الزبالة» بتاع البيت.
كل مشروع فيه كلاس زي كده اسمه Helpers أو Utils أو CommonService. الاسم نفسه اعتراف بضعف التماسك — لأنك معرفتش تسمّيه بغرض واحد.
تطبيق .NET الـ Single Responsibility Principle هو نفسه «تماسك عالي» بصياغة تانية: «الكلاس يكون ليه سبب واحد للتغيير».
لاحظ: السبب مش «يعمل حاجة واحدة» — دي صياغة مضلّلة. OrderService ممكن تعمل 10 حاجات، طول ما الـ 10 دول بيتغيّروا مع بعض ولنفس السبب.
فخ شائع ⚠️ تقسيم الملفات بالنوع التقني (Controllers/، Services/، Repositories/) بيدّي إحساس بالترتيب لكنه بيقلّل التماسك: حاجات ميزة «الطلبات» متفرّقة في 5 مجلدات، وحاجات مالهاش علاقة ببعض (طلبات + مستخدمين + تقارير) مرصوصة في نفس المجلد.
النقطة دي هي بالظبط نقطة انطلاق الـ Vertical Slice — الجزء 6.
القاعدة الذهبية الحاجات اللي بتتغيّر مع بعض، لازم تعيش مع بعض. دي أهم جملة في الموديول كله — واسمها التقني Common Closure Principle.

المفهوم 03 و 04

Separation of Concerns  +  The Dependency Rule

مفهومين بيتبنى عليهم شكل كل معمارية هنشوفها بعد كده.

Separation of Concerns فصل الاهتمامات
التعريف الدقيق كل جزء من النظام يتعامل مع نوع واحد من الاهتمام. و«الاهتمام» (Concern) يعني سبب وجود: قواعد الشغل حاجة، حفظ البيانات حاجة تانية، شكل الـ JSON حاجة ثالثة، الأمان حاجة رابعة.
تشبيه 🏥 في المستشفى: الدكتور بيشخّص، والصيدلي بيصرف، والاستقبال بيسجّل، والمحاسبة بتحصّل. كلهم بيخدموا نفس المريض، بس محدش بيعمل شغل التاني.
تخيّل دكتور بيشخّص وبيحصّل الفلوس وبيكتب الفاتورة وبيرتّب الأرشيف — ده بالظبط الـ Controller اللي فيه 300 سطر.
فخ شائع ⚠️ فصل الاهتمامات مش معناه «اعمل مجلد لكل نوع». ده فصل شكلي. الفصل الحقيقي إن الجزء يقدر يتغيّر لوحده.
لو عندك Services/ وRepositories/ بس أي تغيير في الـ Repository بيكسر الـ Service ⇒ انت قسّمت المجلدات ومقسّمتش الاهتمامات.
The Dependency Rule قاعدة اتجاه الاعتمادية
التعريف الدقيق الاعتماديات لازم تشاور في اتجاه واحد: من المتغيّر ناحية الثابت.
الكود اللي فيه قواعد شغلك يبقى ثابت نسبيًا، والكود اللي بيتعامل مع التقنيات (قواعد بيانات، مكتبات، بروتوكولات) متغيّر.
⇒ التقنية تعتمد على قواعد الشغل، مش العكس.
تشبيه 🏗️ البيت بيتبني من الأساس لفوق. الدور الخامس بيعتمد على الأساس — والأساس ما بيعتمدش على الدور الخامس.
لو عكست الاتجاه (الأساس بيعتمد على الديكور)، أول ما تغيّر الديكور تهدّ البيت.
إزاي تشوفها بعينك في .NET افتح ملفات الـ .csproj وشوف مين بيعمل ProjectReference لمين. الرسمة دي هي معماريتك الحقيقية — مش الرسمة اللي في الـ Wiki.
لو مشروع Domain بيعمل reference لـ Infrastructure ⇒ خلاص، أي كلام عن Clean Architecture بعد كده مجرد أسماء مجلدات.
ليه الاتجاه ده بالذات؟ لأن الأشياء الثابتة ما بتجرّش وراها تغييرات. قواعد شغلك («الفاتورة لازم يكون ليها سطر واحد على الأقل») هتفضل صح لو غيّرت SQL Server بـ PostgreSQL، ولو غيّرت REST بـ gRPC. فمنطقي إن الحاجات المتقلّبة هي اللي تعتمد عليها.
اربط المفهومين ببعض Separation of Concerns بتقولك «قسّم». The Dependency Rule بتقولك «الأسهم بين الأقسام تمشي في أنهي اتجاه».
التقسيم من غير اتجاه = طبقات بتشد في بعض. والاتجاه من غير تقسيم = خط واحد طويل. محتاج الاتنين مع بعض.
المفهوم 05

Dependency Inversion Principle — المفتاح كله

لو فيه مفهوم واحد بس تطلع بيه من الموديول ده، خلّيه ده.

DIP: High-level modules should not depend on low-level modules. Both should depend on abstractions.
الجملة الأصلية للمبدأ — نفكّكها جزء جزء
DIP
اختصار Dependency Inversion Principle = مبدأ عكس الاعتمادية. الحرف D في SOLID.
High-level
المستوى العالي — الكود اللي فيه سياسة الشغل: «الطلب يتحفظ وبعدين العميل ياخد إشعار».
ده اللي بيمثّل قيمة شركتك، وهو نفسه لو اتغيّرت التقنية.
low-level
المستوى المنخفض — تفاصيل التنفيذ: EF Core، SMTP، Redis، HttpClient.
«منخفض» هنا مش تقليل — معناها أقرب للماكينة، مش أقل أهمية.
should not depend on
ما ينفعش يعتمد على — يعني ما ينفعش OrderService تعرف اسم كلاس زي SqlOrderRepository أو تعمل له new أو تستورد الـ namespace بتاعه.
abstractions
التجريدات — في C# دي الـ interface أو الـ abstract class.
حاجة بتوصف «إيه المطلوب» من غير ما تقول «إزاي هيتعمل».
Both

المفهوم 06

Abstraction Leakage — لما التجريد يبقى شكلي

أشهر طريقة يتهد بيها كل اللي بنيناه من غير ما حد ياخد باله.

Leaky Abstraction التجريد المُسرِّب
التعريف الدقيق تجريد بيبان إنه بيخفي التفاصيل، لكنه بيسرّب حاجة من العالم اللي تحته — فاللي بيستخدمه مضطر يعرف التفاصيل عشان يستخدمه صح.
تشبيه 🚰 الحنفية تجريد ممتاز: بتفتحها فتنزل ميّة، ومش لازم تعرف حاجة عن المواسير.
بس لو قالولك «متفتحش المطبخ والحمّام في نفس الوقت وإلا الضغط يقع» ⇒ التجريد سرّب. بقيت مضطر تفهم المواسير عشان تستخدم الحنفية.
الحالة الأشهر في .NET ⚠️ واجهة مستودع بترجّع IQueryable<Order>:
public interface IOrderRepository { IQueryable<Order> Query(); // ← التسريب }
العلامة اللي تكشف أي تسريب اسأل: «هل أقدر أكتب تنفيذ تاني للواجهة دي بتقنية مختلفة تمامًا، من غير ما أكسر أي حد بيستخدمها؟»
لو الإجابة لأ ⇒ الواجهة مش تجريد، دي مجرد Wrapper.
مثال محلول: ليه IQueryable بالذات بيهد المعمارية؟

  1. بيسرّب قدرات المزوّد

    IQueryable معناه «أي استعلام LINQ ينفع». وده كلام مش دقيق — لأن اللي بينفع فعليًا بيتحدّد بـ مزوّد الاستعلام. نفس السطر بيشتغل مع EF Core وبيرمي NotSupportedException مع مزوّد تاني.

  2. بينقل قرار الأداء لمكان غلط

    الطبقة اللي فوق بقت هي اللي بتكتب .Include() و.AsNoTracking() و.Skip().Take(). يعني قرارات قاعدة البيانات اتنقلت لقلب المنطق — وهو بالظبط اللي كنا بنهرب منه.

  3. بيخلّي التنفيذ المتأخر لغم

    الاستعلام ما بيتنفّذش وقت ما تكتبه — بيتنفّذ لما حد يعدّ عليه. فممكن الـ DbContext يكون اتقفل خلاص ⇒ ObjectDisposedException في الإنتاج وانت مش فاهم جت منين.

  4. البديل: واجهة بتتكلم بلغة الشغل

    بدل Query()، اكتب ميثودز بأسماء مقصودة:
    Task<IReadOnlyList<Order>> GetOverdueAsync(DateOnly asOf, CancellationToken ct);
    دلوقتي التنفيذ حر يستخدم EF أو Dapper أو Stored Procedure — واللي بيستخدمه مش فارقة معاه.

استثناء أمين في مسارات القراءة البحتة (تقارير، شاشات عرض)، استخدام IQueryable أو حتى SQL مباشر جوّه مسار القراءة قرار سليم ومقصود — لأنك هنا مش بتحمي قواعد شغل، انت بتعرض بيانات.

Layered / N-Tier نقطة البداية

المعمارية اللي 90% من مشاريع .NET بدأت بيها — وليه بتتدهور مع الوقت.

النمط 01

Layered Architecture — المعمارية الطبقية

قبل ما ننتقدها: هي كانت اختراع عظيم، ولسه مناسبة لحالات كتير.

Layered Architecture المعمارية الطبقية N-Tier
التعريف الدقيق تقسيم النظام لطبقات أفقية حسب نوع المسؤولية التقنية، وكل طبقة بتكلّم اللي تحتها بس.
الشكل الكلاسيكي: Presentation ← Business ← Data Access.
تشبيه 🍰 تورتة بطبقات. كل طبقة ليها طعم مختلف، وبتاكلها من فوق لتحت.
المشكلة: عايز تاخد «قطعة واحدة» (ميزة واحدة)؟ لازم تقطع عبر كل الطبقات — وده بالظبط اللي بيحصل في الكود.
شكلها في .NET حل فيه 3 مشاريع: Shop.Web · Shop.BLL · Shop.DAL.
(BLL = Business Logic Layer · DAL = Data Access Layer)
إمتى تكون قرار ممتاز فعلاً مشروع صغير أو متوسط، فريق من 1–4 أفراد، منطق شغل بسيط (CRUD في الغالب)، وعمر متوقع قصير أو متوسط.
هنا أي معمارية أعقد = خسارة صافية.

تتبّع طلب واحد من أوله لآخره: إنشاء طلب شراء
  1. HTTP Client
    المستخدم بيبعت POST /orders ومعاه جسم JSON فيه بيانات الطلب.
    لحد اللحظة دي مفيش سطر واحد من كودك اشتغل — ده مجرد نص ماشي على الشبكة. بنبدأ التتبّع من هنا عشان تفضل واخد بالك إن الـ HTTP وسيلة نقل، مش جزء من منطق شغلك.
  2. Presentation Layer
    مشروع Shop.Web: الـ OrdersController بيستقبل الطلب ويحوّل الـ JSON لكائن CreateOrderDto.
    الخطوة دي موجودة عشان الطبقات اللي تحت ما تشوفش الويب أصلاً. من غيرها هتلاقي نفسك بتمرّر HttpContext لجوّه، وساعتها اختبار أبسط قاعدة عمل هيحتاج سيرفر ويب شغّال.
  3. Business Logic Layer
    الـ Controller بينادي OrderService.Create(dto) في مشروع Shop.BLL.
    لاحظ إن الاستدعاء لتحت — الويب عارف الـ Service، والـ Service ما تعرفش إن فيه ويب. الاتجاه ده هو اللي بيخلّي نفس الـ Service تشتغل من Worker أو Console App من غير تعديل.
  4. Business Rules
    هنا القواعد الحقيقية: هل العميل موجود؟ هل المخزون كفاية؟ هل السعر صالح؟
    دي الخطوة الوحيدة اللي ليها قيمة تجارية في التتبّع كله — الباقي نقل وترجمة. لو القواعد دي اتسربت لجوّه الـ Controller، هتضطر تكرّرها في كل مدخل جديد للنظام، وأول مرة تنسى واحدة هتبيع حاجة مش موجودة.
  5. Data Access Layer
    الـ Service بتنادي OrderRepository.Add(entity) في مشروع Shop.DAL.
    الـ Repository بيخفي تفاصيل التخزين عن منطق الشغل. من غيره الـ Service هتبقى مليانة SQL، وأي تغيير في اسم عمود هيرجّعك تعدّل في قلب قواعد العمل.
  6. EF Core · SQL Server
    الـ Repository بيعمل SaveChanges() على الـ DbContext، والـ ORM بيترجم الكائن لجملة INSERT وينفّذها جوّه معاملة واحدة.
    ودي نقطة الحقيقة: قبل السطر ده مفيش حاجة اتسجّلت فعلاً.
  7. Presentation Layer
    النتيجة بترجع لفوق بنفس الترتيب بالعكس، والـ Controller بيحوّلها لـ HTTP 201 Created + JSON فيه معرّف الطلب.
    الرجوع بيعدّي على نفس المحطات — يعني كل طبقة بتتحاسب مرتين في الطلب الواحد، رايح وجاي.
الطلب بيعدّي على 3 مشاريع و5 ملفات عشان يعمل حاجة واحدة.
خد بالك من الرقم ده — هنرجعله.

فرق مصطلح مهم: Layer مقابل Tier Layer = تقسيم منطقي في الكود (مجلدات/مشاريع على نفس الجهاز).
Tier = تقسيم فيزيائي (كل جزء على سيرفر مختلف).
ممكن يبقى عندك 3 Layers على 1 Tier — وده الشائع.

Anemic Domain Model

كلاسات فيها خصائص بس (get; set;) من غير أي سلوك. القواعد كلها في الـ Services.
النموذج بقى مجرد «حقيبة بيانات».

🌳

Rich Domain Model

الكلاس فيه البيانات + القواعد اللي بتحميها. مستحيل تخلّيه في حالة غلط.
النموذج بقى «حارس على نفسه».

Order.csC# / .NET 9
// ══════════════ ❌ Anemic — حقيبة بيانات ══════════════
public class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = "New";
    public decimal Total { get; set; }
    public List<OrderLine> Lines { get; set; } = new();
}

// أي كود في الدنيا يقدر يعمل ده — ومحدش هيمنعه:
order.Status = "Shpped";      // خطأ إملائي، والكومبايلر مبسوط
order.Total  = -500;          // إجمالي بالسالب
order.Lines.Clear();          // طلب مشحون من غير أصناف

// ══════════════ ✅ Rich — النموذج بيحمي نفسه ══════════════
public sealed class Order
{
    private readonly List<OrderLine> _lines = [];

    public OrderId Id { get; private set; }          // مفيش set من بره
    public OrderStatus Status { get; private set; }  // enum مش string
    public Money Total => _lines.Aggregate(Money.Zero, (a, l) => a + l.LineTotal);
    public IReadOnlyList<OrderLine> Lines => _lines;  // للقراءة بس

    private Order() { }   // لـ EF Core بس

    public static Order Draft(CustomerId customer) =>
        new() { Id = OrderId.New(), Status = OrderStatus.Draft, CustomerId = customer };

    public void AddLine(ProductId product, int qty, Money unitPrice)
    {
        // القاعدة عايشة جنب البيانات اللي بتحميها
        if (Status != OrderStatus.Draft)
            throw new DomainException("مينفعش تضيف صنف بعد تأكيد الطلب");
        if (qty <= 0)
            throw new DomainException("الكمية لازم تكون أكبر من صفر");

        var existing = _lines.FirstOrDefault(l => l.ProductId == product);
        if (existing is not null) existing.IncreaseQuantity(qty);
        else _lines.Add(new OrderLine(product, qty, unitPrice));
    }

    public void Confirm()
    {
        if (_lines.Count == 0)
            throw new DomainException("مينفعش تأكّد طلب فاضي");
        Status = OrderStatus.Confirmed;
    }
}
الفروق الخمسة اللي تركّز عليها في الكود ده 1. private set بدل set ⇒ التغيير بيعدّي من ميثود ليها اسم ومعنى.
2. _lines قائمة خاصة، والبرّه بيشوف IReadOnlyList ⇒ محدش يقدر يمسح أصناف من ورا الطلب.
3. Total بقى محسوب مش مخزّن ⇒ مستحيل يبقى مختلف عن الأصناف.
4. OrderStatus نوع مُعرَّف (enum) بدل string ⇒ الخطأ الإملائي بقى خطأ ترجمة مش خطأ إنتاج.
5. Draft() ميثود إنشاء ⇒ مفيش طريقة تعمل طلب في حالة ناقصة.
🤔
وهنا نبقى أمناء: النموذج الفقير مش دايمًا غلط لو الجدول ده مجرد بيانات مرجعية (دول، عملات، أنواع)، وقواعده صفر — فالنموذج الغني عليه مبالغة. كلاس بخصائص بس هو الحل المظبوط.
القاعدة: الغنى بيستحق تمنه لما يكون فيه قواعد يحميها. من غير قواعد، الغنى بيبقى مجرد بيروقراطية.
تمرين 7 — حوّل الفقير لغنيصعب

عندك BankAccount فقير بخصائص: Balance، IsClosed، OverdraftLimit. والقواعد الحالية متفرّقة في 3 خدمات مختلفة:

  • مينفعش تسحب لو الحساب مقفول.
  • مينفعش الرصيد ينزل تحت −OverdraftLimit.
  • مينفعش تقفل حساب رصيده مش صفر.

اكتب الشكل الغني. وإيه المكسب الملموس؟

شوف الحل
public sealed class BankAccount { public Money Balance { get; private set; } public Money OverdraftLimit { get; private set; } public bool IsClosed { get; private set; } public void Withdraw(Money amount) { if (IsClosed) throw new DomainException("الحساب مقفول"); if (amount <= Money.Zero) throw new DomainException("المبلغ لازم يكون موجب"); if (Balance - amount < -OverdraftLimit) throw new DomainException("تجاوز حد السحب على المكشوف"); Balance -= amount; } public void Close() { if (Balance != Money.Zero) throw new DomainException("لازم الرصيد صفر قبل القفل"); IsClosed = true; } }

المكسب الملموس (مش نظري):

  • مكان واحد للحقيقة: لو دخلت قناة جديدة (تطبيق موبايل، API لشريك، Background Job) — القواعد بتشتغل تلقائيًا. في الشكل الفقير كنت هتنساها في قناة على الأقل.
  • اختبار في ملّي ثانية: الاختبارات دي مالهاش أي علاقة بقاعدة بيانات — 200 اختبار بيخلصوا في أقل من ثانية.
  • الرسائل بقت بلغة الشغل: «تجاوز حد السحب» بدل SqlException: CHECK constraint.
لاحظ حاجة مهمة الكلاس ده مش عارف حاجة عن EF Core ولا HTTP ولا الـ JSON. وده معناه إنه هيفضل صح لو غيّرت أي حاجة من دول.
ودي بالظبط الفكرة اللي Clean Architecture مبنية عليها — وهي اللي جاية دلوقتي.

Use Case / Interactor حالة الاستخدام
التعريف الدقيق كلاس بينفّذ سيناريو واحد من سيناريوهات التطبيق، من أوله لآخره. اسمه بيبقى فعل: ConfirmOrder، RegisterCustomer، IssueRefund.
الكلمة Interactor هي الاسم الأصلي عند Uncle Bob — نفس الحاجة بالظبط.
تشبيه 🍳 الـ Entity = المكوّنات وقواعدها (البيض بيستوي عند حرارة معيّنة).
الـ Use Case = الوصفة (هات البيض، اضربه، حطه على النار، قدّمه).
الوصفة بتنسّق، والمكوّنات ليها طبيعتها اللي مش بتتغيّر بالوصفة.
تطبيق .NET عمليًا بيتكتب كـ Handler (مع MediatR أو من غيرها)، بياخد Command أو Query ويرجّع Result.

Boundary Interface واجهة الحدود
التعريف الواجهة اللي بتقف على حدّ الدايرة وبتحدّد إزاي اللي بره يكلّم اللي جوه (والعكس).
نوعين: Input Boundary (اللي الـ Controller بينادي عليها) وOutput Boundary (اللي الـ Use Case بينادي عليها عشان يوصل لبره).
فخ ⚠️ في .NET معظم الفرق بتستغنى عن الـ Input Boundary وبتنادي الـ Handler مباشرة — وده مقبول تمامًا. الواجهات اللي بتفرق فعلاً هي بتاعة الخروج (تخزين، دفع، إشعار).

namespace Shop.Application.Orders;

// ═══ 1) الأمر: بيانات الدخول بس — مفيش سلوك ═══
public sealed record ConfirmOrderCommand(Guid OrderId, string ConfirmedBy);

// ═══ 2) حالة الاستخدام: بترتّب الخطوات وبس ═══
public sealed class ConfirmOrderHandler(
    IOrderRepository orders,
    IInventoryService inventory,     // واجهة مملوكة للـ Application
    IUnitOfWork uow,
    ILogger<ConfirmOrderHandler> log)
{
    public async Task<Result> HandleAsync(
        ConfirmOrderCommand cmd, CancellationToken ct)
    {
        // (أ) هات الحالة — من غير ما تعرف من فين
        var order = await orders.GetByIdAsync(new OrderId(cmd.OrderId), ct);
        if (order is null)
            return Result.Fail("الطلب مش موجود");

        // (ب) تحقق من حاجة برّانية — عن طريق عقد
        if (!await inventory.CanReserveAsync(order.Lines, ct))
            return Result.Fail("المخزون مش كافي");

        // (ج) القاعدة نفسها بتتنفّذ جوّه الكيان — مش هنا
        order.Confirm(cmd.ConfirmedBy);

        // (د) احفظ كوحدة واحدة
        await uow.SaveChangesAsync(ct);

        log.LogInformation("Order {OrderId} confirmed", order.Id);
        return Result.Ok;
    }
}
اقرا الكود ده بالعربي الـ Handler ده ما بيحتويش ولا قاعدة شغل واحدة — هو منسّق بس: «هات الطلب، اتأكد من المخزون، خلّي الطلب يأكّد نفسه، احفظ».
القاعدة الحقيقية («مينفعش تأكّد طلب فاضي») عايشة جوّه order.Confirm().
ولاحظ: الأربع اعتماديات كلهم واجهات، فتقدر تختبر الـ Handler ده بمزيّفات في الذاكرة وتغطّي كل المسارات (طلب مش موجود / مخزون ناقص / نجاح) في 3 اختبارات سريعة.
وILogger استثناء مقبول — لأنه جزء من الـ BCL وتجريد فعلاً.
المفهوم 13

DTO مقابل Domain Model

أكتر سؤال بيتسأل: «ليه أعمل نسختين من نفس الحاجة؟»

DTO — Data Transfer Object كائن نقل بيانات
التعريف الدقيق كائن غرضه الوحيد نقل بيانات عبر حدّ (من الـ API للعميل، أو من العميل للتطبيق). مفيش فيه سلوك، ومفيش فيه قواعد.
تشبيه 📦 الـ Domain Model = المنتج بمواصفاته وقيوده.
الـ DTO = كرتونة الشحن.
الكرتونة شكلها بيتحدّد حسب شركة الشحن، والمنتج مالوش دعوة بده. ولو غيّرت شركة الشحن، بتغيّر الكرتونة مش المنتج.
ليه الفصل ده مهم عمليًا — 4 أسباب ملموسة
  • أمان: لو رجّعت الكيان مباشرة، ممكن تسرّب PasswordHash أو InternalCost من غير ما تقصد.
  • الإفراط في الحماية: الكيان الغني مفيهوش set عام — فمعظم أدوات الـ Serialization هتتعب معاه.
  • استقرار العقد: إعادة تسمية خاصية داخلية ما ينفعش تكسر تطبيق الموبايل بتاع عميلك.
  • الشكل المختلف: الشاشة عايزة CustomerName — والكيان عنده CustomerId بس.
فخ شائع ⚠️ استخدام نفس الكلاس كـ Request وResponse وEntity وDB Model.
بيوفّر عليك 20 دقيقة النهاردة، وبيربط عقد الـ API بشكل جدولك للأبد. أول ما تغيّر عمود، عميل بيتكسر.
مثال محلول: نفس الطلب بثلاث أشكال مختلفة

📥 Request DTO

record CreateOrderRequest( Guid CustomerId, List<LineDto> Lines, string? Coupon);

بيمثّل اللي العميل بيبعته. مفيش فيه Id ولا Status — لأن دول مش من حق العميل يحدّدهم.

💛 Domain Entity

class Order { OrderId Id { get; private set; } OrderStatus Status { get; private set; } void AddLine(...) void Confirm() }

بيمثّل الشغل وقواعده. أنواع قوية وسلوك، ومفيش أي حاجة ليها علاقة بالـ HTTP.

📤 Response DTO

record OrderSummaryDto( Guid Id, string Status, string CustomerName, decimal Total, int LineCount);

بيمثّل اللي الشاشة محتاجاه. فيه CustomerName (مش في الكيان) ومفيهوش تفاصيل داخلية.

النقطة اللي بتقنع أي حد الثلاثة دول بيتغيّروا لأسباب مختلفة تمامًا: الأول بيتغيّر لما شكل الفورم يتغيّر، والتاني لما قواعد الشغل تتغيّر، والتالت لما التصميم يتغيّر.
لما تجمعهم في كلاس واحد، بتربط ثلاث إيقاعات تغيير ببعض — وده تعريف الارتباط العالي بالحرف.

هل لازم يعملوا DTO لكل كيان؟

شوف الحل

لأ، مش لازم — والإصرار على ده هنا هيبقى تكلفة بلا مقابل.

  • سبب الـ DTO الأول (استقرار العقد) مش موجود: مفيش عميل خارجي، والنشر متزامن.
  • سبب تاني (شكل مختلف) ضعيف في شاشات CRUD.
  • سبب تالت (الأمان) لسه موجود — فلو فيه حقول حساسة، اعملها DTO.

القرار المتوازن:

  • الكيانات اللي فيها حقول حساسة أو منطق ⇒ DTO.
  • جداول مرجعية بسيطة (دول، وحدات، فئات) ⇒ ارجّع الكيان مباشرة وخلاص.
  • لو بعدين ظهر عميل خارجي ⇒ ساعتها ضيف DTO للنقطة دي بس.
المبدأ اللي وراه كل قاعدة معمارية ليها سبب. اسأل عن السبب الأول: «أنا بحمي نفسي من إيه هنا؟»
لو السبب مش موجود في حالتك، القاعدة بتتحوّل لطقس. وأسوأ ما في المعماريات إنها تتحوّل لطقوس بتتنفّذ بدون فهم.

Port مقابل Adapter

Port المنفذ
التعريف واجهة مملوكة للتطبيق، مكتوبة بلغة التطبيق، بتوصف حاجة محتاجها أو حاجة بيقدّمها — من غير أي ذكر لتقنية.

علامة المنفذ السليم توقيعه مفهوم لواحد من الشغل مش مبرمج:
Task<PaymentResult> ChargeAsync(Money amount, PaymentMethod method)

Adapter المحوّل
التعريف تنفيذ عايش برّه بيترجم بين لغة التطبيق ولغة التقنية. هو اللي بيعرف Stripe وSQL وKafka.

ممكن يكون عندك أكتر من محوّل لنفس المنفذ في نفس الوقت (إنتاج / اختبار / بيئة تجريبية).

محوّلات Driving مقابل Driven

الفرق بينهم مش شكلي — هو اللي بيحدّد مين بيملك الواجهة.

Driving (Primary) Adapters vs Driven (Secondary) Adapters
أربع كلمات بتتلخبط دايمًا — نفكّكهم
Driving
القائد / اللي بيسوق. الجهة اللي بتبدأ التفاعل وبتنادي على التطبيق.
أمثلة: HTTP Controller، CLI، Background Job، مستهلك رسائل، والاختبارات كمان.
Primary
أساسي — اسم تاني لنفس الحاجة. سُمّي كده لأنه بيمثّل الاستخدام «الأساسي» للتطبيق.
Driven
المقود / اللي بيتساق. الجهة اللي التطبيق بينادي عليها عشان تخدمه.
أمثلة: قاعدة البيانات، ناقل الرسائل، بوابة الدفع، الإيميل، الكاش.
Secondary
ثانوي — اسم تاني لنفس الحاجة. «ثانوي» هنا مش معناها أقل أهمية، معناها إنه بيستجيب مش بيبدأ.
القاعدة اللي تفرّق بيها في ثانية: اسأل مين بيبدأ المكالمة؟ لو الطرف الخارجي هو اللي بينادي التطبيق ⇒ Driving. لو التطبيق هو اللي بينادي الطرف الخارجي ⇒ Driven.

🎮 Driving — مين بيملك الواجهة؟

التطبيق بيقدّم الواجهة، والمحوّل بيستهلكها.
الواجهة هنا هي حالات الاستخدام نفسها (PlaceOrderHandler).

النتيجة العملية: تقدر تضيف gRPC أو GraphQL أو شاشة Console جنب الـ REST من غير ما تلمس سطر واحد في التطبيق.

🔧 Driven — مين بيملك الواجهة؟

التطبيق بيعرّف الواجهة (المنفذ)، والمحوّل بينفّذها.
ودي بالظبط الـ DIP اللي شرحناها في الجزء 1.

النتيجة العملية: تغيير مزوّد الدفع = كلاس جديد + سطر في Program.cs. صفر تعديل في المنطق.

صنّف كل واحد: Driving ولا Driven؟

  1. مستهلك رسائل من RabbitMQ بيسمع حدث «الدفع نجح».
  2. ناشر رسائل بيبعت حدث «الطلب اتأكّد» على نفس الـ RabbitMQ.
  3. Redis للكاش.
  4. Webhook جاي من Stripe.

  • 1 ⇒ Driving. الرسالة هي اللي بتوصل وبتشغّل التطبيق. لاحظ إن نفس التقنية (RabbitMQ) ممكن تبقى في الاتجاهين!
  • 2 ⇒ Driven. هنا التطبيق هو اللي بيبادر ويقول «ابعت».
  • 3 ⇒ Driven. التطبيق بيسأل الكاش.
  • 4 ⇒ Driving. Stripe هي اللي بتنادي عليك.
    وده بيوضّح نقطة مهمة: نفس المزوّد ممكن يكون Driven لما تخصم منه، وDriving لما يبعتلك Webhook.
  • 5 ⇒ Driving. الاختبار محوّل قيادة بالظبط زي الـ HTTP.
    ودي البصيرة الجميلة في المسدّس: الاختبارات مش «حاجة جنبية» — هي مستخدم من مستخدمي تطبيقك، وليها نفس الحقوق.
ليه التصنيف ده مهم عمليًا؟ لأنه بيحدّد مين بيكتب الواجهة:
في الـ Driving، التطبيق بيقدّم واجهة والعالم بيستهلكها.
في الـ Driven، التطبيق بيطلب واجهة والعالم بينفّذها.
لو لخبطت الاتجاه ده، هتلاقي نفسك بتعرّف واجهات في مشروع الـ Web وتحاول الدومين يستخدمها — وهترجع لنقطة الصفر.

public sealed class StripePaymentGateway(
    IStripeClient stripe,
    ILogger<StripePaymentGateway> log) : IPaymentGateway
{
    public async Task<PaymentResult> ChargeAsync(
        Money amount, PaymentMethodToken token, CancellationToken ct)
    {
        try
        {
            // ترجمة (أ): من لغتنا للغة Stripe — القروش بدل الجنيه
            var options = new PaymentIntentCreateOptions
            {
                Amount   = (long)(amount.Amount * 100),
                Currency = amount.Currency.ToLowerInvariant(),
                PaymentMethod = token.Value,
                Confirm  = true
            };

            var intent = await stripe.CreateIntentAsync(options, ct);

            // ترجمة (ب): من لغة Stripe للغتنا
            return intent.Status switch
            {
                "succeeded"       => new PaymentResult.Succeeded(intent.Id),
                "requires_action" => new PaymentResult.Declined("محتاج تأكيد إضافي"),
                _                 => new PaymentResult.Declined(intent.Status)
            };
        }
        catch (StripeException ex)
        {
            // ترجمة (ج): الخطأ كمان بيتترجم — ممنوع يتسرّب للتطبيق
            log.LogError(ex, "Stripe charge failed");
            return new PaymentResult.Failed("مزوّد الدفع مش متاح دلوقتي");
        }
    }
}

    public sealed record Response(Guid OrderId, decimal Total, string Status);

                .Where(p => ids.Contains(p.Id))
                .ToDictionaryAsync(p => p.Id, ct);

            if (products.Count != ids.Distinct().Count())
                return TypedResults.BadRequest("فيه منتج مش موجود");

            // الدومين هو اللي بيفرض القواعد — مش الشريحة
            var order = Order.Draft(new CustomerId(req.CustomerId), clock.GetUtcNow());
            foreach (var line in req.Lines)
            {
                var p = products[line.ProductId];
                order.AddLine(p.Id, line.Quantity, p.Price);   // ممكن يرمي DomainException
            }
            order.Confirm();

            db.Orders.Add(order);
            await db.SaveChangesAsync(ct);

            return TypedResults.Created(
                $"/orders/{order.Id.Value}",
                new Response(order.Id.Value, order.Total.Amount, order.Status.ToString()));
        }
    }

    // ─── 5) تعريف نقطة الدخول — في نفس الملف كمان ───
    public static void MapEndpoint(IEndpointRouteBuilder app) =>
        app.MapPost("/orders", async (
                Request req, Handler handler, CancellationToken ct)
                    => await handler.HandleAsync(req, ct))
           .WithName("PlaceOrder")

           .RequireAuthorization()
           .WithOpenApi();

// ══════ Value Object: النوع بيحمي نفسه من الإنشاء ══════
public readonly record struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        // التحقق وقت الإنشاء ⇒ مستحيل يوجد Money غلط في الذاكرة
        if (string.IsNullOrWhiteSpace(currency) || currency.Length != 3)
            throw new DomainException("كود العملة لازم 3 حروف");
        if (decimal.Round(amount, 2) != amount)
            throw new DomainException("أقصى دقة رقمين عشريين");

        Amount = amount;
        Currency = currency.ToUpperInvariant();
    }

    public static Money Egp(decimal a) => new(a, "EGP");
    public static Money Zero => new(0, "EGP");

    // عمليات بتحمي قاعدة شغل: ممنوع تجمع عملات مختلفة
    public static Money operator +(Money a, Money b)
    {
        if (a.Currency != b.Currency)
            throw new DomainException($"مينفعش تجمع {a.Currency} مع {b.Currency}");
        return new(a.Amount + b.Amount, a.Currency);
    }

    public static Money operator *(Money m, int qty) => new(m.Amount * qty, m.Currency);
    public override string ToString() => $"{Amount:N2} {Currency}";
}

Aggregate التجميعة
التعريف الدقيق مجموعة كيانات وكائنات قيمة بتتعامل كـوحدة واحدة في التغيير والحفظ، وليها جذر واحد (Aggregate Root) هو المدخل الوحيد ليها من بره.
تشبيه 📄 عقد ورقي: البنود جوّه العقد مالهاش معنى لوحدها، وما ينفعش حد يعدّل بند من غير ما يعدّي على العقد ككل ويوقّع عليه.
العقد = الجذر · البنود = كيانات داخلية · التوقيع = القاعدة اللي الجذر بيفرضها.
التعريف اللي هيفيدك أكتر في الشغل الـ Aggregate هو حدود المعاملة (Transaction Boundary).
يعني: كل اللي جوّاه لازم يبقى متّسق في نفس اللحظة، وكل اللي بره ممكن يبقى متّسق بعد شوية.
وده بيخلّي سؤال «أحفظ إيه مع إيه في نفس الـ Transaction؟» له إجابة واضحة.
فخ شائع ⚠️ تصميم الـ Aggregate حسب شكل الشاشة أو علاقات الجداول.
الشاشة عايزة تعرض الطلب + بيانات العميل + المنتجات ⇒ فبنحط كل ده في aggregate واحد.
غلط. العرض حاجة والتعديل حاجة تانية. للعرض اعمل استعلام قراءة، وسيب الـ Aggregate صغير.
إزاي تكتشف حدوده — السؤال الذهبي «إيه القواعد اللي لازم تفضل صح في كل لحظة من غير أي تأخير؟»
مثال: «إجمالي الطلب = مجموع سطوره» ⇒ لازم فوري ⇒ يبقى السطور جوّه الـ Aggregate.
مثال: «رصيد نقاط العميل يتحدّث بعد الطلب» ⇒ يقبل تأخير ثانية ⇒ يبقى العميل aggregate تاني، والربط بحدث.
One aggregate per transaction · reference by ID · keep them small
الثلاث قواعد الذهبية لتصميم الـ Aggregates
One aggregate per transaction
تجميعة واحدة في المعاملة الواحدة. تعدّل واحدة بس وتحفظ.
لو محتاج تعدّل تانية ⇒ استخدم Domain Event وخلّيها تتعدّل في معاملة تانية.
السبب: قفل أقل ⇒ تزاحم أقل ⇒ أداء أعلى وأعطال تزامن أقل.
reference by ID
الإشارة بالمعرّف. الـ Order يحمل CustomerId — مش كائن Customer كامل.
السبب: لو حملت الكائن، هتحمّل شجرة كاملة من الداتابيز في كل قراءة، وهتفتح باب إن حد يعدّل العميل من جوّه الطلب.
keep them small
خلّيها صغيرة. كل ما كبرت: قراءة أبطأ، وقفل أوسع، واحتمال تعارض أعلى.
القاعدة العملية: لو الـ aggregate بيحمّل أكتر من عشرات السجلات، ده جرس إنذار.
صمّم تجميعات صغيرة، تعدّل واحدة في المرة، واربطها ببعض بالمعرّفات والأحداث. الثلاث قواعد دول بيحلّوا معظم مشاكل التزامن قبل ما تحصل.

public sealed class Order : AggregateRoot<OrderId>
{
    private readonly List<OrderLine> _lines = [];

    // ── كل الخصائص للقراءة من بره ──
    public CustomerId CustomerId { get; private set; }  // معرّف بس — مش كائن Customer
    public OrderStatus Status { get; private set; }
    public DateTimeOffset PlacedAt { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();

    // الإجمالي محسوب — مستحيل يتعارض مع السطور
    public Money Total => _lines.Aggregate(Money.Zero, (sum, l) => sum + l.LineTotal);

    private Order() { }   // EF Core

    // ── الإنشاء عن طريق ميثود ليها اسم من الشغل ──
    public static Order Draft(CustomerId customer, DateTimeOffset now)
    {
        var order = new Order
        {
            Id = OrderId.New(),
            CustomerId = customer,
            Status = OrderStatus.Draft,
            PlacedAt = now
        };
        return order;
    }

    // ══════ القواعد (Invariants) بتتفرض هنا وبس ══════
    public void AddLine(ProductId product, int qty, Money unitPrice)
    {
        EnsureDraft();
        if (qty <= 0)
            throw new DomainException("الكمية لازم أكبر من صفر");
        if (_lines.Count >= 50)
            throw new DomainException("أقصى عدد أصناف في الطلب 50");

        var existing = _lines.FirstOrDefault(l => l.ProductId == product);
        if (existing is not null) existing.Increase(qty);
        else _lines.Add(OrderLine.Create(Id, product, qty, unitPrice));
    }

    public void RemoveLine(ProductId product)
    {
        EnsureDraft();
        _lines.RemoveAll(l => l.ProductId == product);
    }

    public void Confirm(DateTimeOffset now)
    {
        EnsureDraft();
        if (_lines.Count == 0)
            throw new DomainException("مينفعش تأكّد طلب من غير أصناف");
        if (Total.Amount <= 0)
            throw new DomainException("إجمالي الطلب لازم يكون موجب");

        Status = OrderStatus.Confirmed;

        // الحدث بيتسجّل جوّه الـ Aggregate — مش بيتبعت دلوقتي
        Raise(new OrderConfirmed(Id, CustomerId, Total, now));
    }

    public void Cancel(string reason, DateTimeOffset now)
    {
        if (Status is OrderStatus.Shipped or OrderStatus.Delivered)
            throw new DomainException("مينفعش إلغاء طلب اتشحن — استخدم الإرجاع");
        if (string.IsNullOrWhiteSpace(reason))
            throw new DomainException("لازم سبب للإلغاء");

        Status = OrderStatus.Cancelled;
        Raise(new OrderCancelled(Id, reason, now));
    }

    private void EnsureDraft()
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException($"مينفعش التعديل والطلب في حالة {Status}");
    }
}

2. CustomerId معرّف مش كائن ⇒ الـ aggregate فضل صغير، ومحدش يقدر يعدّل العميل من جوّه الطلب.
3. كل ميثود عامة بتبدأ بالتحقق من الحالة (EnsureDraft) ⇒ القواعد مش ممكن تتنسى.
4. Total محسوب مش مخزّن ⇒ استحال يبقى فيه تعارض بين الإجمالي والسطور.
5. رسائل الأخطاء بلغة الشغل ⇒ تقدر تعرضها للمستخدم مباشرة.
6. Raise() بتسجّل حدث جوّه الكائن — ما بتبعتوش دلوقتي. وده مقصود، والسبب في السلايد الجاية.

نظام حجز فنادق. القواعد:

  1. مينفعش غرفتين محجوزتين في نفس التاريخ لنفس الغرفة (فوري وإجباري).
  2. لما يتم الحجز، نقاط ولاء العميل بتزيد.
  3. الحجز فيه ضيوف، وكل ضيف له بيانات.
  4. الفاتورة بتتولّد بعد تسجيل الخروج.

ليه التقسيم ده بالذات؟

  • القاعدة 1 فورية ⇒ لازم تتحمي جوّه aggregate واحد مع قفل. وخلّينا RoomAvailability لكل غرفة مش لكل الفندق — عشان حجز غرفة 101 ما يقفلش غرفة 205.
    لو عملتها aggregate واحد للفندق كله، كل الحجوزات هتقف في طابور واحد.
  • القاعدة 2 بتقبل تأخير ⇒ حدث ReservationConfirmed والنقاط بتتحدّث بعده. لو النقاط فشلت، الحجز ما يتلغيش — بتتعاد المحاولة.
  • القاعدة 4 بتحصل بعدين ⇒ الفاتورة aggregate مستقلة بتتولّد من حدث GuestCheckedOut.
الدرس الأهم حدود الـ Aggregate بتترسم من قواعد الاتساق، مش من علاقات الجداول.
السؤال دايمًا: «القاعدة دي لازم تكون صح في نفس اللحظة، ولا تقبل تتأخر ثواني؟»
لازم فوري ⇒ نفس الـ aggregate. تقبل تأخير ⇒ aggregate تاني + حدث.
ولاحظ إن الإجابة على السؤال ده بتيجي من خبير الشغل مش من المطوّر.

Domain Event حدث الدومين
التعريف الدقيق حقيقة حصلت خلاص في الدومين ومهمة لخبير الشغل. الاسم دايمًا في الماضي: OrderConfirmed، PaymentFailed، StockDepleted.
تشبيه 📢 إعلان في مطار: «الرحلة 302 هبطت». اللي مهتم بيتصرّف (الأمتعة، الجوازات، التاكسي).
والمذيع مش عارف مين بيسمع — ولو دخل قسم جديد بكرة، بيسمع من غير ما المذيع يتغيّر.
ليه بنسجّله ومنبعتوش فورًا؟ لأن لسه ممكن الحفظ يفشل! لو بعتّه لحظة Confirm() وبعدين SaveChanges رمت خطأ، هتبقى بعتّ إيميل لعميل عن طلب ما اتحفظش.
⇒ سجّل الحدث جوّه الـ aggregate، وابعته بعد نجاح الحفظ.
المكسب المعماري Order ما بيعرفش حاجة عن المخزون ولا الإيميل ولا النقاط. هو بس بيقول «اتأكّد».
⇒ تضيف سلوك جديد لما الطلب يتأكّد = كلاس معالج جديد بس، صفر تعديل في الدومين.

// ══════ 1) القاعدة المشتركة لكل جذر تجميعة ══════
public abstract class AggregateRoot<TId>
{
    private readonly List<IDomainEvent> _events = [];

    public TId Id { get; protected set; } = default!;
    public IReadOnlyList<IDomainEvent> Events => _events;

    protected void Raise(IDomainEvent e) => _events.Add(e);
    public void ClearEvents() => _events.Clear();
}

// ══════ 2) الحدث نفسه — record بسيط، بيانات وبس ══════
public interface IDomainEvent { DateTimeOffset OccurredAt { get; } }

public sealed record OrderConfirmed(
    OrderId OrderId,
    CustomerId CustomerId,
    Money Total,
    DateTimeOffset OccurredAt) : IDomainEvent;

// ══════ 3) النشر بعد الحفظ — جوّه DbContext ══════
public sealed class ShopDbContext(
    DbContextOptions<ShopDbContext> options,
    IDomainEventDispatcher dispatcher) : DbContext(options)
{
    public DbSet<Order> Orders => Set<Order>();

    public override async Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        // (أ) اجمع كل الأحداث من الكيانات المتتبَّعة قبل الحفظ
        var roots = ChangeTracker
            .Entries<AggregateRoot<OrderId>>()
            .Where(e => e.Entity.Events.Count > 0)
            .Select(e => e.Entity)
            .ToList();

        var events = roots.SelectMany(r => r.Events).ToList();

        // (ب) احفظ الأول — لو فشل، مفيش أي حدث هيتبعت
        var affected = await base.SaveChangesAsync(ct);

        // (ج) نضّف وبعدين انشر
        roots.ForEach(r => r.ClearEvents());
        foreach (var e in events)
            await dispatcher.DispatchAsync(e, ct);

        return affected;
    }
}

// ══════ 4) المعالجات — كل واحد مستقل تمامًا ══════
public sealed class ReserveStockOnOrderConfirmed(IStockService stock)
    : IDomainEventHandler<OrderConfirmed>
{
    public Task HandleAsync(OrderConfirmed e, CancellationToken ct) =>
        stock.ReserveAsync(e.OrderId, ct);
}

public sealed class AddLoyaltyPointsOnOrderConfirmed(ILoyaltyService loyalty)
    : IDomainEventHandler<OrderConfirmed>
{
    public Task HandleAsync(OrderConfirmed e, CancellationToken ct) =>
        loyalty.AddPointsAsync(e.CustomerId, (int)(e.Total.Amount / 10), ct);
}
اقرا الترتيب في الميثود SaveChangesAsync — الترتيب ده هو كل الحكاية (أ) بنلمّ الأحداث من الكيانات قبل الحفظ، لأن بعد الحفظ الـ ChangeTracker ممكن يبقى اتنضّف.
(ب) بنحفظ. لو رمى استثناء ⇒ الميثود بتقف هنا ومفيش ولا حدث اتبعت — وده اللي بيمنع «إيميل عن طلب مش موجود».
(ج) بننضّف الأحداث الأول وبعدين ننشر — عشان لو معالج عمل SaveChanges تاني، ما يبعتش نفس الحدث مرة كمان (تكرار لا نهائي).

ملاحظة إنتاجية مهمة: النشر ده في نفس العملية. لو المعالج فشل (الخدمة واقعة مثلاً)، الحدث بيضيع.
للأنظمة اللي ما تتحملش الضياع، بتحط الأحداث في جدول في نفس المعاملة (Outbox Pattern) وخدمة خلفية بتقراه وتبعت مع إعادة محاولة.

النمط 06

CQRS — فصل القراءة عن الكتابة

فكرة بسيطة جدًا، بس اسمها مخيف واستخدامها بيتبالغ فيه.

CQRS = Command Query Responsibility Segregation
أربع كلمات — كل واحدة ليها معنى محدّد
Command
أمر — عملية بتغيّر حالة النظام. اسمها فعل أمر: PlaceOrder، CancelOrder.
بترجّع نجاح/فشل — مش بترجّع بيانات للعرض.
Query
استعلام — عملية بتقرا بس وما بتغيّرش أي حاجة.
بترجّع بيانات جاهزة للعرض، ومفيش فيها ولا قاعدة شغل.
Responsibility
المسؤولية — يعني الشغلانة اللي الكود ده مسؤول عنها.
Segregation
الفصل — كلمة أقوى من «تقسيم». يعني مسارين منفصلين تمامًا: نماذج مختلفة، وكود مختلف، وممكن تخزين مختلف.
«افصل الكود اللي بيغيّر عن الكود اللي بيقرا، لأن لكل واحد فيهم احتياجات مختلفة تمامًا.»
CQRS فصل مسؤوليات الأوامر والاستعلامات
ليه أصلاً؟ — السبب الحقيقي لأن الكتابة والقراءة احتياجاتهم متعاكسة:
الكتابة عايزة نموذج غني بقواعد وحماية وثبات.
القراءة عايزة بيانات مسطّحة جاهزة للشاشة بأسرع شكل.
لما تجبرهم على نفس النموذج، بتضحّي بواحد فيهم — وغالبًا بالاتنين.
تشبيه 🏪 السوبرماركت: المخزن منظّم للإدخال والجرد (كراتين، أرفف عالية، تواريخ). الرفوف منظّمة للعرض والبيع (منتجات مفردة، أسعار، ترتيب جذاب).
نفس البضاعة، تنظيمين مختلفين، لكل واحد غرضه.
أشهر سوء فهم ⚠️ CQRS ≠ قاعدتين بيانات. ولا يساوي Event Sourcing. ولا يحتاج Message Bus.
أبسط شكل من الـ CQRS = نموذجين مختلفين في الكود على نفس قاعدة البيانات.
ودي أغلب الحالات اللي هتحتاجها فعلاً.

المستويات الثلاثة — اطلع درجة درجة حسب الحاجة

  1. المستوى 1 — نماذج مختلفة، نفس قاعدة البيانات ابدأ هنا

    الأمر بيستخدم EF Core وكيانات غنية. الاستعلام بيستخدم Dapper أو AsNoTracking ويرجّع DTO مسطّح.
    التكلفة: شبه صفر · المكسب: وضوح + أداء قراءة أحسن بمراحل.
    القراءة بتوفّر عادةً 40–70% من الوقت لأنها بتلغي التتبّع والتحميل الزايد.

  2. المستوى 2 — جداول قراءة (Read Models) في نفس القاعدة

    جداول مسطّحة متبنية من الأحداث، مخصوصة للشاشات (مثلاً OrderSummaries فيه اسم العميل والإجمالي جاهزين).
    التكلفة: منطق تحديث + Eventual Consistency · المكسب: استعلام بجدول واحد بدل 6 وصلات.

  3. المستوى 3 — مخزن قراءة منفصل تمامًا

    الكتابة في SQL، والقراءة من Elasticsearch أو MongoDB أو Redis، والمزامنة بالأحداث.
    التكلفة: عالية جدًا (تزامن، تأخير، تعارض، مراقبة مزدوجة) · المكسب: توسّع قراءة شبه لا نهائي.
    ما توصلش هنا غير لما تكون الأرقام أجبرتك — مش لأنه شكله متقدّم.

⏳
التمن الأساسي: الاتساق النهائي من المستوى 2 وطالع، بيبقى فيه فجوة زمنية بين الكتابة وظهورها في القراءة — عادة من 50ms لثواني.
يعني المستخدم يضغط «حفظ» وبعدين يشوف قايمة قديمة ⇒ «الحفظ ما اشتغلش!».

// ═══════════ جهة الكتابة: نموذج غني + قواعد ═══════════
public sealed record CancelOrderCommand(Guid OrderId, string Reason)
    : IRequest<Result>;

public sealed class CancelOrderHandler(
    IOrderRepository orders,
    IUnitOfWork uow,
    TimeProvider clock) : IRequestHandler<CancelOrderCommand, Result>
{
    public async Task<Result> Handle(CancelOrderCommand cmd, CancellationToken ct)
    {
        // بنحمّل التجميعة كاملة — لأننا محتاجين قواعدها
        var order = await orders.GetByIdAsync(new OrderId(cmd.OrderId), ct);
        if (order is null) return Result.NotFound("الطلب مش موجود");

        try
        {
            order.Cancel(cmd.Reason, clock.GetUtcNow());   // القاعدة جوّه الدومين
        }
        catch (DomainException ex)
        {
            return Result.Fail(ex.Message);       // رسالة بلغة الشغل
        }

        await uow.SaveChangesAsync(ct);              // هنا بتتنشر الأحداث
        return Result.Ok;                          // ما بيرجّعش بيانات عرض
    }
}

// ═══════════ جهة القراءة: نموذج مسطّح + سرعة ═══════════
public sealed record GetOrdersPageQuery(Guid CustomerId, int Page, int Size)
    : IRequest<IReadOnlyList<OrderRowDto>>;

// نوع مخصوص للشاشة دي بالظبط — مش كيان الدومين
public sealed record OrderRowDto(
    Guid Id, string Status, decimal Total,
    int ItemCount, string CustomerName, DateTimeOffset PlacedAt);

public sealed class GetOrdersPageHandler(IDbConnection db)
    : IRequestHandler<GetOrdersPageQuery, IReadOnlyList<OrderRowDto>>
{
    private const string Sql = """
        SELECT  o.Id, o.Status, o.TotalAmount AS Total,
                COUNT(l.Id) AS ItemCount, c.FullName AS CustomerName, o.PlacedAt
        FROM    Orders o
        JOIN    Customers  c ON c.Id = o.CustomerId
        LEFT JOIN OrderLines l ON l.OrderId = o.Id
        WHERE   o.CustomerId = @CustomerId
        GROUP BY o.Id, o.Status, o.TotalAmount, c.FullName, o.PlacedAt
        ORDER BY o.PlacedAt DESC
        OFFSET @Skip ROWS FETCH NEXT @Take ROWS ONLY;
        """;

    public async Task<IReadOnlyList<OrderRowDto>> Handle(
        GetOrdersPageQuery q, CancellationToken ct)
    {
        // مفيش تجميعات ولا تتبّع ولا قواعد — استعلام واحد ونتيجة جاهزة
        var rows = await db.QueryAsync<OrderRowDto>(new CommandDefinition(Sql,
            new { q.CustomerId, Skip = (q.Page - 1) * q.Size, Take = q.Size },
            cancellationToken: ct));

        return rows.ToList();
    }
}

صنّف كل واحدة، والحالات المخادعة اشرح ليه:

  1. «هات تفاصيل الطلب رقم كذا».
  2. «احجز الغرفة دي».
  3. «ولّد تقرير PDF واحفظه في التخزين وارجّع رابطه».
  4. «سجّل إن المستخدم شاف الإشعار» — والواجهة عايزة عدد الإشعارات الجديدة بعدها.
  5. «ابحث في المنتجات» — والبحث بيسجّل الكلمة في جدول إحصائيات.
شوف الحل
  • 1 ⇒ Query واضح. قراءة بحتة.
  • 2 ⇒ Command واضح. بيغيّر الحالة وله قواعد.
  • 3 ⇒ Command. مخادعة! «تقرير» بتوحي بقراءة، لكن العملية بتكتب ملف وبتحفظ سجل ⇒ ليها أثر جانبي ⇒ أمر.
    وكمان: لو اتنفّذت مرتين هتولّد ملفين — ده أثر يهم.
  • 4 ⇒ Command، والعدد بيرجع في نتيجة الأمر.
    خالف القاعدة النظرية («الأمر ما يرجّعش بيانات») عن قصد وبوعي: لو عملتها أمر بعده استعلام، هتقع في فخ الاتساق النهائي وهتعرض عدد قديم.
    الرجوع البسيط بعد الأمر حل عملي مقبول — القواعد للخدمة مش للعبادة.
  • 5 ⇒ Query + حدث. البحث نفسه استعلام، وتسجيل الإحصائية يتنشر كحدث ويتعالج في الخلفية.
    لو خلّيته أمر، هتضطر تعمل معاملة كتابة في كل عملية بحث ⇒ ضغط ضخم بلا لازمة.
القاعدة المرنة اسأل: «لو نفّذت العملية دي 10 مرات ورا بعض، هيبقى فيه فرق؟»

CQRS — امشي بالدرجات

المستوى 1 (نماذج قراءة منفصلة على نفس القاعدة):
لما شاشة تقارير بقت بطيئة، أو لما تلاقي نفسك بتحمّل كيانات كاملة عشان تعرض 4 أعمدة.
ده تقريبًا دايمًا قرار صح.

المستوى 2 (جداول قراءة):
لما استعلام مهم فيه 5+ وصلات وبقى فوق 500ms، والفهارس خلصت حيلتها.

المستوى 3 (مخزن منفصل):
لما نسبة القراءة للكتابة تعدّي 100:1 وتكون قست وأثبتّ إن ده عنق الزجاجة.
وقتها بس.
