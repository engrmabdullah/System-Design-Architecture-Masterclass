اللحظة اللي السيرفر الواحد بيقف فيها

مش بيقف فجأة. بيبعت إشارات قبلها بشهور — والموديول ده كله عن قراءة الإشارات دي والتصرّف.

1,800RPS — الحمل الطبيعي، كله تمام
3,400RPS — الـ p99 بدأ يتضاعف
4,100RPS — الطابور اتراكم والسيرفر وقع
اقرا الأرقام دي كده لاحظ إن السيرفر ما وقعش عند 4,100 لأن ده «حده الأقصى». هو وقع لأنه عدّى نقطة اللي بيستقبل فيها أكتر مما بينجز. من اللحظة دي الطابور بيكبر، والذاكرة بتمتلي بطلبات مستنية، والـ Timeout بيبدأ يضرب — وكل عميل بيعيد المحاولة فبيزوّد الحمل. دي حلقة بتنتهي بانهيار كامل.
🎯

الموديول ده بيجاوب على 3 أسئلة

  1. إزاي أزوّد الطاقة؟ — سيرفر أكبر ولا سيرفرات أكتر، وإمتى كل واحد.
  2. إزاي أوزّع الحمل بعدل؟ — الـ Load Balancer وخوارزمياته.
  3. إزاي أمنع عطل واحد إنه يوقّع كل حاجة؟ — أنماط الصمود.
⚠️

اللي مش هنقوله

مش هنقول «استخدم Kubernetes وخلاص» ولا «زوّد سيرفرات». كل قرار هنا هيطلع من رقم أو قانون: كام سيرفر بالظبط؟ ليه الخوارزمية دي مش التانية؟ وإيه التمن اللي بتدفعه؟

🧠
الجملة اللي هتتكرر في كل جزء التوسّع مش «زيادة موارد» — التوسّع هو «إزالة المشترَك». كل حاجة مشتركة بين السيرفرات (قفل، ذاكرة، جدول، قاعدة بيانات واحدة) هي سقف مخفي بيمنع الزيادة إنها تتحوّل لإنتاجية.
01

التوسّع الرأسي والأفقي Scale Up vs Scale Out

أول قرار بتاخده، وأكتر قرار الناس بتاخده غلط — في الاتجاهين.

المفهوم 01

Vertical Scaling — التوسّع الرأسي

«خلّي الماكينة أكبر». أبسط حل موجود — ولذلك بيتم الاستهزاء بيه ظلمًا.

Vertical Scaling (Scale Up) التوسّع الرأسي
التعريف الدقيق إنك تزوّد موارد الماكينة الواحدة: معالجات أكتر (vCPU)، ذاكرة أكبر (RAM)، قرص أسرع (NVMe)، أو كارت شبكة أعرض.
عدد الماكينات ما بيتغيرش — الماكينة نفسها هي اللي بتكبر.
تشبيه 🍔 مطعمك فيه شيف واحد بيطلّع 20 وجبة/ساعة والزباين بقوا عايزين 60. التوسّع الرأسي = تجيب شيف أسطورة بيطلّع 60 لوحده، وتديله فرن أكبر وسكاكين أحسن.
المطبخ زي ما هو، الإدارة زي ما هي، ومفيش تنسيق جديد محتاج يتعمل. بس لو الشيف ده مرض — المطعم قفل.
تطبيق .NET تطبيق ASP.NET Core بيستفيد من الرأسي فورًا ومن غير ما تغيّر سطر: الـ Thread Pool بيكبر مع عدد الأنوية، والـ Server GC بيشتغل بـ heap مستقل لكل نواة فبيقلّل التوقفات، والـ Connection Pool بيقدر يفتح اتصالات أكتر.
غيّر حجم الماكينة، اعمل restart، خلاص.
فخ شائع ⚠️ الناس بتفتكر إن التكلفة خطّية: ضعف الأنوية = ضعف السعر. ده صحيح في الوسط، وغلط تمامًا في الطرف الأعلى. آخر ماكينة في العائلة بتكلّف 2 إلى 4 أضعاف اللي قبلها مقابل 2× موارد بس.
وكمان: الترقية بتحتاج إعادة تشغيل ⇒ توقف فعلي إلا لو عندك نسخة تانية أصلاً.
إمتى تستخدمه لما تكون لسه تحت السقف (وهنحسبه بعد شوية)، أو لما يكون عندك مكوّن صعب توزيعه بطبيعته: قاعدة بيانات علائقية بتكتب، أو خدمة بتحتفظ بحالة في الذاكرة، أو تطبيق قديم Legacy مش مصمّم للتوزيع.
المفهوم 02

Horizontal Scaling — التوسّع الأفقي

«خلّي الماكينات أكتر». مفيش سقف نظري — بس التمن تعقيد بيدخل من كل باب.

Horizontal Scaling (Scale Out) التوسّع الأفقي
التعريف الدقيق إنك تضيف ماكينات إضافية بنفس المواصفات، وتحط قدامهم موزّع (Load Balancer) يوزّع الطلبات عليهم. الماكينة الواحدة زي ما هي — العدد هو اللي بيكبر.
تشبيه 🍔 نفس المطعم: بدل الشيف الأسطورة، تجيب 3 شيفات عاديين.
الطاقة بقت 60 وجبة، ولو واحد مرض المطعم لسه شغّال بـ 40.
بس دلوقتي محتاج حاجات ما كانتش موجودة قبل كده: مين يوزّع الطلبات عليهم، وإزاي أعرف إن واحد فيهم تعبان، وإزاي أضمن إن الطلب ما يتعملش مرتين.
دي بالظبط الـ 3 حاجات اللي الموديول ده بيشرحها.
تطبيق .NET الأفقي بيشتغل بشرط واحد: الخدمة تكون Stateless. يعني ممنوع static Dictionary فيه بيانات مستخدمين، وممنوع InMemory Session، وممنوع IMemoryCache لبيانات لازم تكون موحّدة.
الحل: Redis للحالة المشتركة + Data Protection Keys مخزّنة برّه.
فخ شائع ⚠️ «هزوّد سيرفرات وخلاص» — وبعدين تكتشف إن كل السيرفرات بتكلّم نفس قاعدة البيانات. فأنت ما زوّدتش الطاقة، أنت زوّدت عدد اللي بيخبطوا على نفس الباب. الأداء ممكن يقل فعلاً بسبب التنافس على الاتصالات والأقفال.
إمتى تستخدمه لما تكون قربت من سقف الماكينة الواحدة، أو لما تكون محتاج High Availability حقيقي (نسخة واحدة = نقطة فشل)، أو لما يكون حملك متذبذب فعايز تزوّد وتقلّل حسب الوقت.
المقارنة

وجهًا لوجه — كل بُعد على حدة

⬆️

Scale Up — رأسي

  • صفر تغيير في الكود — الترقية عملية بنية تحتية بحتة.
  • مفيش شبكة بين الأجزاء ⇒ مفيش Latency إضافي.
  • الـ Transaction بتفضل بسيطة على ماكينة واحدة.
  • تشخيص الأعطال أسهل بمراحل: لوج واحد، ذاكرة واحدة.
  • سقف فيزيائي — بيخلص وما فيش بعده.
  • الترقية = إعادة تشغيل = توقف.
  • الماكينة نفسها SPOF.
  • التكلفة أسّية في الطرف الأعلى.
VS
➡️

Scale Out — أفقي

  • مفيش سقف نظري — تقدر توصل لآلاف الماكينات.
  • التكلفة خطّية تقريبًا (ماكينات رخيصة متكررة).
  • فشل ماكينة = فقدان جزء من الطاقة مش انقطاع.
  • تقدر تنشر بالتدريج (Rolling Update) بدون توقف.
  • الكود لازم يكون Stateless — وده مش مجاني.
  • محتاج موزّع + فحص صحة + اكتشاف خدمات.
  • الشبكة دخلت المعادلة ⇒ فشل جزئي وتأخير.
  • الاتساق بقى مشكلة حقيقية.
c5.24xlarge — 96 vCPU / 192 GiB RAM / 25 Gbps / $4.08 per hour
ده سطر مواصفات ماكينة سحابية. كل جزء فيه بيقولّك حاجة مختلفة تمامًا
c5
عائلة الماكينة. الحرف c اختصار Compute optimized — يعني نسبة المعالج للذاكرة عالية (مصمّمة للحسابات).
في مقابلها: m = General purpose (متوازنة)، r = Memory optimized (ذاكرة ضخمة، للكاش وقواعد البيانات).
والرقم 5 = الجيل. الجيل الأحدث بيبقى أسرع وأرخص لنفس المواصفات.
24xlarge
الحجم داخل العائلة. الترتيب: large → xlarge → 2xlarge → 4xlarge … وكل خطوة بتضاعف الموارد تقريبًا.
24xlarge يعني 24 ضعف حجم الـ xlarge — وده تقريبًا آخر العائلة.
96 vCPU
96 نواة معالجة افتراضية. الحرف v = virtual.
مهم: الـ vCPU غالبًا بيبقى خيط (Thread) مش نواة فيزيائية كاملة — يعني 96 vCPU ≈ 48 نواة حقيقية بتقنية SMT. عشان كده الأداء الحقيقي مش بيتضاعف زي ما الرقم بيوحي.
192 GiB
192 جيبي بايت ذاكرة. لاحظ GiB مش GB: الـ GiB = 1024³ بايت، والـ GB = 1000³. الفرق بينهم حوالي 7% — وده بيفرق فعلاً لما تحسب سعة كاش كبيرة.
25 Gbps
سرعة الشبكة: 25 Gigabit per second. انتبه: بت مش بايت. اقسم على 8 ⇒ ~3.1 GB/s فعليًا.
لو خدمتك بترجّع ردود كبيرة، ممكن الشبكة تبقى هي عنق الزجاجة قبل المعالج خالص.
$4.08/hr
4.08 دولار في الساعة. اضربها في 730 ساعة في الشهر ⇒ $2,978 شهريًا للماكينة الواحدة.
وده قبل التخزين والشبكة والنسخ الاحتياطي.
الماكينة دي فيها 96 نواة افتراضية و192 جيجا ذاكرة وشبكة 25 جيجابت، وبتكلّف حوالي 3 آلاف دولار شهريًا. السطر ده بيديك السقف اللي التوسّع الرأسي بيوصله — وبيديك السعر اللي هتقارن بيه الحل الأفقي.

التلات كلمات دي بيفسّروا ليه الرأسي بيقف حتى لو عندك فلوس
fault domain
نطاق الفشل — المساحة اللي عطل واحد بيأثّر عليها كلها. ماكينة واحدة = نطاق فشل واحد. لو اللوحة الأم باظت، أو الكهربا في الرف قطعت، أو النواة (Kernel) عملت Panic — النظام كله راح. مهما كانت الماكينة قوية، توافرها سقفه حوالي 99.9% وخلاص.
NUMA
اختصار Non-Uniform Memory Access = وصول غير موحّد للذاكرة.
في الماكينات الكبيرة الذاكرة بتتقسّم على أكتر من معالج فيزيائي. المعالج بيوصل لـ «ذاكرته» بسرعة، ولذاكرة المعالج التاني أبطأ بـ 1.5 إلى 2 مرة.
يعني نص الوصولات في ماكينتك العملاقة أبطأ من المتوقّع — والكود ما بيعرفش ده أصلاً.
coherency
تماسك الكاش (Cache Coherency). كل نواة عندها كاش خاص، ولما نواة تعدّل قيمة لازم كل النوى التانية تعرف إن نسختها بقت قديمة.
عدد رسائل التنسيق دي بيزيد بمعدل n × (n−1) — يعني تربيعي مع عدد النوى. عند 96 نواة الرقم ده بقى ضخم، وجزء معتبر من طاقة المعالج بيروح في «التنسيق» مش في الشغل.
السقف الحقيقي للتوسّع الرأسي مش السعر — هو إن عندك نطاق فشل واحد، وإن الماكينة نفسها بتضيّع جزء متزايد من طاقتها في التنسيق الداخلي كل ما كبرت. القانون التربيعي ده هنشوفه تاني في آخر الموديول باسم Universal Scalability Law.

تمرين 1 — رأسي ولا أفقي؟متوسط

لكل حالة، اختار الاتجاه واكتب السبب في سطر:

  1. قاعدة بيانات SQL Server بتكتب 3,000 عملية/ثانية، والاستغلال 80%.
  2. خدمة API عديمة الحالة بتخدم 12,000 RPS على ماكينة c5.24xlarge واحدة.
  3. نظام كاشير لازم يفضل شغّال حتى لو الماكينة وقعت — الحمل بسيط جدًا.
شوف الحل
  • 1 → رأسي أولاً. جهة الكتابة في قاعدة علائقية أصعب حاجة توزّعها (محتاج Sharding وتغيير في الكود والاستعلامات). زوّد الذاكرة والأقراص أولاً، وحسّن الفهارس. الأفقي هنا آخر حل مش أوله.
  • 2 → أفقي إجباري. أنت أصلاً على آخر ماكينة في العائلة — مفيش «أكبر» بسعر معقول. وكمان عندك SPOF بيخدم 12 ألف طلب/ثانية، وده خطر غير مقبول.
  • 3 → أفقي، رغم إن الحمل بسيط. هنا القرار مالوش علاقة بالحمل خالص — المطلوب Availability مش Throughput. ماكينتين صغيرتين أحسن من ماكينة كبيرة.
الدرس المستفاد في كل حالة، السؤال مش «إيه الأحدث؟» ولا «إيه اللي الشركات الكبيرة بتعمله؟». السؤال هو: إيه القيد اللي بيوجعني دلوقتي؟ لو القيد طاقة ⇒ شوف السقف والسعر. لو القيد توافر ⇒ الأفقي هو الحل الوحيد مهما كان الحمل صغير. لو القيد طبيعة المكوّن (كتابة علائقية) ⇒ الرأسي بيشتري وقت غالي.

المفهوم 03

Load Balancer — إيه اللي بيحصل جوّاه بالظبط

مش «صندوق بيوزّع». خلينا نشوف الخطوات الفيزيائية اللي بيعملها على كل طلب.

Load Balancer موزّع الأحمال
التعريف الدقيق مكوّن بيقف قدّام مجموعة سيرفرات متطابقة، بيستقبل كل الطلبات على عنوان واحد (Virtual IP)، وبيقرّر لكل طلب يروح لأنهي سيرفر — وبيشيل من الدورة أي سيرفر مش سليم.
تشبيه 🏦 موظّف الاستقبال في بنك فيه 8 شبابيك.
• الزبون بيدخل من باب واحد ⇒ الـ VIP.
• الموظّف شايف كل الشبابيك وعارف مين فاضي ⇒ خوارزمية التوزيع.
• شباك قفل عشان الموظّف راح يشرب حاجة ⇒ الموزّع بيوقف يوجّهله ⇒ Health Check.
• الزبون عمره ما عرف إن فيه 8 شبابيك أصلاً — هو شايف بنك واحد.
تطبيق .NET في عالم .NET عندك YARP (Yet Another Reverse Proxy) — موزّع مكتوب بـ C# بيشتغل كتطبيق ASP.NET Core عادي، فتقدر تكتب سياسات التوجيه بكود وتستخدم كل الـ Middleware اللي تعرفه.
وبرّه ده: nginx · HAProxy · Azure Application Gateway · AWS ALB/NLB.
فخ شائع ⚠️ الموزّع نفسه بيبقى SPOF جديد! حطيت موزّع عشان تحمي من فشل السيرفرات… وخلقت نقطة فشل واحدة قدّامهم كلهم.
الحل: موزّعين على الأقل في وضع Active-Active خلف DNS أو Anycast IP — وده اللي مزوّدي السحابة بيعملوه لك تلقائيًا في الخدمات المُدارة.
إمتى تستخدمه من ثاني سيرفر بالظبط. مفيش «توسّع أفقي من غير موزّع» — البديل الوحيد هو توزيع من جهة العميل (Client-side) وده أصعب بكتير وهنشوفه في جزء اكتشاف الخدمات.

الخطوات الست اللي بيعملها على كل طلب

  1. يقبل الاتصال

    العميل بيعمل TCP handshake مع الموزّع مش مع السيرفر. يعني الموزّع بيدفع تكلفة الاتصالات المفتوحة كلها.

  2. يفك التشفير (لو L7)

    بيعمل TLS Termination — بيفك تشفير الطلب عشان يقدر يقرا الـ Path والـ Headers. من غير ده مش هيقدر يوجّه بذكاء.

  3. يختار سيرفر

    بيشغّل خوارزمية التوزيع على قائمة السيرفرات السليمة بس — مش على القائمة كلها. دي نقطة مهمة الناس بتنساها.

  4. يفتح/يعيد استخدام اتصال

    بيمسك مجموعة اتصالات جاهزة للسيرفرات (Connection Pool) عشان ما يعملش handshake جديد كل مرة — ده لوحده بيوفّر 1–3 ms على كل طلب.

  5. ينقل البيانات ويعدّل الترويسات

    بيضيف X-Forwarded-For (عنوان العميل الحقيقي) وX-Forwarded-Proto. من غيرهم تطبيقك هيفتكر إن كل المستخدمين جايين من عنوان الموزّع.

  6. يقيس ويقرّر

    بيسجّل زمن الرد وكود الحالة لكل سيرفر — ودي المدخلات اللي بيبني عليها Passive Health Check والخوارزميات الذكية.

نقف ونفكّك 🔍

يعني إيه «طبقة» أصلاً؟ — L4 مقابل L7

الاختصارين دول بتلاقيهم في كل توثيق موزّع أحمال، ونادرًا حد بيقولّك معناهم بالظبط.

L4 = TCP/UDP (IP : Port)  ·  L7 = HTTP (Host, Path, Header, Cookie)
السطر ده بيلخّص فرق ضخم في القدرات. نفكّكه رمز رمز
L
اختصار Layer = طبقة. الشبكة متقسّمة لـ 7 طبقات في نموذج OSI، كل طبقة بتغلّف اللي تحتها.
الفكرة: كل طبقة بتضيف «مظروف» حوالين البيانات. كل ما تطلع لفوق، بتعرف معلومات أكتر — بس بتدفع وقت أطول عشان تفتح المظاريف.
L4
الطبقة الرابعة — Transport. هنا بيعيش TCP وUDP.
اللي الموزّع بيشوفه على المستوى ده: عنوان المصدر، عنوان الوجهة، ورقم المنفذ.
هو مش عارف إنت بتطلب صفحة إيه ولا حتى إن ده HTTP أصلاً — بيشوف بايتات ماشية بين نقطتين.
L7
الطبقة السابعة — Application. هنا بيعيش HTTP وgRPC وWebSocket.
على المستوى ده الموزّع بيفهم الطلب: عارف الـ Path والـ Method والـ Headers والـ Cookies.
يعني يقدر ياخد قرارات زي: «كل اللي بيبدأ بـ /api/orders يروح للمجموعة دي».
IP : Port
العنوان + رقم المنفذ. زي «شارع كذا، شقة رقم 443».
الـ IP بيحدّد الجهاز، والـ Port بيحدّد أنهي برنامج جوّه الجهاز. دي كل المعلومات المتاحة للموزّع في L4.
Host
ترويسة Host: shop.example.com — بتقول أنهي موقع مطلوب. عشان كده تقدر تشغّل 50 موقع مختلف على نفس العنوان والمنفذ، والموزّع الـ L7 بيفرّق بينهم. ده مستحيل في L4.
Cookie
الموزّع الـ L7 يقدر يقرا ويكتب Cookies — وده اللي بيخلّي Sticky Sessions ممكنة (وهنشوف ليه دي فخ).
الفرق ببساطة: L4 بيوزّع «اتصالات» وهو أعمى بالنسبة للمحتوى فبيبقى سريع جدًا، وL7 بيوزّع «طلبات» وهو فاهم المحتوى فبيبقى ذكي جدًا. والاختيار بينهم قرار معماري مش تفضيل.
صورة تثبّت الفرق تخيّل ساعي بريد. الـ L4 بياخد الجواب ويوصّله للعمارة الصح من غير ما يفتحه — سريع جدًا، بس لو الجواب المفروض يروح لقسم معيّن جوّه العمارة، هو مش هيعرف.
الـ L7 بيفتح الجواب ويقراه ويقرّر يروح لأنهي مكتب بالظبط — أبطأ شوية، بس بيقدر يعمل حاجات مستحيلة على التاني.

Round Robin — والنسخة الموزونة منه

Round Robin التوزيع بالتناوب
التعريف الدقيق عدّاد واحد بيلف على قائمة السيرفرات بالترتيب: index = (index + 1) % count. الطلب رقم 1 للسيرفر A، الطلب 2 لـ B، الطلب 3 لـ C، الطلب 4 يرجع لـ A. مفيش أي معرفة بحالة السيرفرات.
تشبيه 🃏 توزيع الكوتشينة على اللاعبين: ورقة لكل واحد بالترتيب، من غير ما تبص هو شايل كام ورقة ولا شكله تعبان ولا لأ. عادل تمامًا في عدد الأوراق، وممكن يبقى ظالم جدًا في وزن الأوراق.
تطبيق .NET في YARP ده اسمه RoundRobin، وهو مش الافتراضي (الافتراضي أذكى منه). في Kubernetes الـ Service بتوزّع بالتناوب على مستوى L4 عبر iptables/IPVS.
فخ شائع ⚠️ «التوزيع عادل» ≠ «الحمل عادل». لو 20% من طلباتك بتاخد 2 ثانية و80% بتاخد 10ms، الـ Round Robin ممكن يرمي 3 طلبات تقيلة ورا بعض على نفس السيرفر — فيبقى مخنوق والباقي فاضي.
وفخ أخطر: مع الاتصالات طويلة العمر (WebSocket، gRPC streaming، HTTP/2) التوزيع بيحصل مرة واحدة عند فتح الاتصال — فسيرفر ممكن يفضل شايل 90% من العملاء لساعات.
إمتى تستخدمه لما تكون الطلبات متجانسة في التكلفة والسيرفرات متطابقة، والاتصالات قصيرة. مثال مثالي: خدمة تصديق توكن بترجّع في 5ms دايمًا.
وكمان: هو خيار ممتاز لما تكون عايز بساطة مطلقة وقابلية تنبؤ في الاختبارات.
Weighted Round Robin التناوب الموزون
التعريف الدقيق نفس التناوب، بس كل سيرفر بياخد نصيب متناسب مع وزنه. سيرفر بوزن 3 بياخد 3 طلبات مقابل كل طلب لسيرفر بوزن 1. الوزن بيتحدّد يدويًا حسب قدرة الماكينة.
تشبيه 🚚 توزيع بضاعة على عربيات مختلفة الحجم: العربية الكبيرة تاخد 3 كراتين والصغيرة كرتونة. مش هتديهم بالتساوي وانت شايف إن واحدة ضعف التانية.
تطبيق .NET في YARP بتحطّه في Metadata للوجهة، وفي nginx بتكتب server app1 weight=3;.
استخدام عملي مهم: Canary Release — تدّي النسخة الجديدة وزن 1 والقديمة 19، يعني 5% من الترافيك بس بيشوف الجديد.
فخ شائع ⚠️ الأوزان بتبقى قديمة وحد ينساها. حطّيت وزن 3 لماكينة قوية، وبعد سنة اتغيّرت الماكينات كلها وبقت متطابقة — والوزن لسه 3. النتيجة: سيرفر بياخد 3 أضعاف الحمل بلا سبب.
وكمان: الوزن بيعبّر عن القدرة النظرية، مش عن الحالة اللحظية. ماكينة قوية بس بتعمل GC دلوقتي لسه بتاخد 3 أضعاف.
إمتى تستخدمه لما يكون الأسطول غير متجانس (أجيال ماكينات مختلفة)، أو في Canary وBlue-Green، أو لتوزيع الترافيك بين مناطق بنسب مقصودة (70/30 مثلاً).
المفهوم 07 و 08

الخوارزميات اللي بتبص على الحالة الفعلية

Least Connections الأقل اتصالات
التعريف الدقيق الموزّع بيمسك عدّاد لكل سيرفر بعدد الطلبات الجارية دلوقتي (اللي اتبعتت ولسه ما رجعش ردها)، وبيدّي الطلب الجديد لصاحب أقل عدّاد. العدّاد بيزيد عند الإرسال وبينقص عند وصول الرد.
تشبيه 🛒 في السوبرماركت: بدل ما تقف في الطابور بالدور، بتبص على كل الطوابير وتقف في أقصرها. ودي فعلاً أذكى، لأنها بتاخد في اعتبارها إن فيه زبون قدّامك عربيته مليانة (طلب تقيل) وواحد شايل حاجتين بس.
تطبيق .NET في YARP السياسة اسمها LeastRequests. وهي الاختيار الصح لما تكون الطلبات مختلفة جدًا في الزمن — زي API فيه استعلامات بسيطة وتقارير تقيلة على نفس السيرفر.
فخ شائع ⚠️ «السيرفر اللي بيفشل بسرعة بيبان أفضل واحد». لو سيرفر بقى بيرجّع 500 فورًا في 1ms، عدّاده هيفضل قريب من الصفر ⇒ الموزّع هيرميله كل الترافيك. دي كارثة معروفة اسمها Black Hole.
الحل: تربطها بفحص صحة سلبي بيشيل السيرفر اللي نسبة أخطائه عالية، مش بس اللي بطيء.
فخ تاني: مع أكتر من موزّع، كل واحد شايف عدّاده هو بس — فالقرار «الأقل» بيبقى محلي مش عام.
إمتى تستخدمه لما يكون تباين زمن الطلبات كبير، أو مع اتصالات طويلة العمر، أو لما يكون عندك موزّع واحد (فالعدّادات دقيقة).
Least Response Time الأقل زمن استجابة
التعريف الدقيق بيجمع بين حاجتين: عدد الاتصالات الجارية × متوسط زمن الاستجابة الأخير. يعني بيقدّر «الزمن المتوقّع لو بعتّ الطلب هنا»، وبيختار الأقل.
متوسط الزمن بيتحسب عادة بـ EWMA (Exponentially Weighted Moving Average) — متوسط بيدّي وزن أكبر للحظات القريبة.
تشبيه 🛒 نفس السوبرماركت، بس دلوقتي بتبص على الطابور وعلى الكاشير كمان: طابور فيه 5 ناس مع كاشير سريع أحسن من طابور فيه 3 مع كاشير جديد بطيء.
تطبيق .NET مش موجودة جاهزة في YARP بالاسم ده، لكن تقدر تكتبها كـ ILoadBalancingPolicy مخصّصة. موجودة جاهزة في HAProxy باسم leastconn مع option httpchk، وفي شبكات الخدمات زي Envoy باسم LEAST_REQUEST مع slow start.
فخ شائع ⚠️ التذبذب (Oscillation). السيرفر A بقى أسرع ⇒ كل الترافيك راح له ⇒ بقى أبطأ ⇒ كل الترافيك راح لـ B ⇒ B بقى أبطأ… النظام بيدخل في موجات بدل ما يستقر.
الحل: نافذة قياس أطول، وتنعيم القيم، وSlow Start للسيرفر الجديد عشان ما ياخدش كل الحمل دفعة واحدة.
إمتى تستخدمه لما يكون الأسطول غير متجانس فعليًا بشكل متغيّر: ماكينات في مناطق مختلفة، أو ماكينات بتشتغل عليها أحمال تانية، أو لما تكون حساس جدًا للـ Tail Latency.
المفهوم 09

IP Hash — التوزيع الثابت حسب العميل

الخوارزمية الوحيدة اللي بتضمن إن نفس العميل يروح لنفس السيرفر — وده مكسب وخطر في نفس الوقت.

IP Hash التجزئة حسب عنوان العميل
التعريف الدقيق بياخد عنوان العميل، يعدّيه على دالة تجزئة، وياخد باقي القسمة على عدد السيرفرات: server = hash(client_ip) % N. النتيجة حتمية: نفس العنوان ⇒ نفس السيرفر دايمًا، من غير ما الموزّع يحفظ أي حالة.
تشبيه 🏥 توزيع المرضى على الأطباء حسب أول حرف في الاسم: من A لـ H عند دكتور 1، ومن I لـ P عند دكتور 2. مفيش سجل محتاج يتحفظ — الاسم لوحده بيحدّد الوجهة.
وطبعًا: لو الأسماء اللي بتبدأ بـ A كتير جدًا، دكتور 1 هيتقتل شغل.
تطبيق .NET مفيدة لما يكون كل سيرفر بيبني Local Cache للعميل: لو نفس المستأجر (Tenant) بيروح لنفس السيرفر، نسبة إصابة الكاش بتقفز.
في YARP ده بيتعمل بـ HashLoadBalancing أو بسياسة مخصّصة على ترويسة زي X-Tenant-Id بدل الـ IP — وده أدق بمراحل.
فخ شائع ⚠️ (اتنين خطيرين) 1) إعادة التوزيع الشاملة: لو سيرفر اتشال أو اتضاف، الـ % N بتتغيّر ⇒ تقريبًا كل العملاء بيتنقلوا لسيرفرات جديدة. كل الكاشات المحلية بقت بلا قيمة في نفس اللحظة ⇒ موجة ضغط هائلة على قاعدة البيانات.
الحل: Consistent Hashing — بتنقل 1/N بس من العملاء.
2) التوزيع غير المتساوي: عملاء كتير ورا نفس الـ NAT (شركة، مشغّل موبايل) بيبانوا عنوان واحد ⇒ سيرفر واحد بياخدهم كلهم.
إمتى تستخدمه لما يكون فيه فايدة حقيقية من الالتصاق: كاش محلي، أو اتصال WebSocket لازم يفضل على نفس العقدة، أو تقسيم بيانات (Sharding) على مستوى الطبقة دي.
ما تستخدمهاش لمجرد إنك عايز الجلسة تفضل شغّالة — ده الفخ اللي جاي بعد شوية.
// ═══ ليه Consistent Hashing أفضل من Modulo ═══ hash % N عند N: 4 → 5 → ~80% من المفاتيح اتنقلت Consistent Hashing → ~20% (1/N) بس اتنقلت

يعني بالبلدي: مع % N إضافة سيرفر واحد بتلغي الكاش عند تقريبًا كل العملاء، ومع الـ Consistent Hashing بتلغيه عند خُمسهم بس. الفرق ده هو اللي بيفرّق بين ترقية عادية وموجة انهيار على قاعدة البيانات.

المفهوم 10

Random with Two Choices — أقوى فكرة في الباب ده

خوارزمية بتكلّف تقريبًا زي العشوائي البحت، وبتدّي نتيجة قريبة من المثالي. خلينا نفهم ليه.

Random with Two Choices العشوائي باختيارين
التعريف الدقيق بدل ما تفحص كل السيرفرات، اختار اتنين عشوائي بس، وقارن حملهم، وابعت للأقل. خلاص.
التكلفة: مقارنة واحدة (O(1)) بدل مسح كل الأسطول (O(n)).
تشبيه 🛒 في سوبرماركت فيه 100 طابور، مستحيل تفحصهم كلهم — هتضيّع وقت أطول من الوقوف نفسه. بس لو بصّيت لاتنين بس عشوائي ووقفت في الأقصر، هتلاقي نتيجتك قريبة جدًا من اللي فحص المية كلهم.
ده مش تخمين — ده نتيجة رياضية مثبتة اسمها Power of Two Choices.
تطبيق .NET في YARP اسمها PowerOfTwoChoices وهي السياسة الافتراضية — يعني لو ما كتبتش حاجة، دي اللي شغالة. موجودة كمان في Envoy وNginx Plus وFinagle.
فخ شائع ⚠️ الناس بتفتكرها «عشوائي مع تحسين بسيط» فبتستهين بيها وتروح للـ Least Connections الكامل — وده بيكلّف مسح كل الأسطول على كل طلب، وبيخلق مشاكل تنسيق بين الموزّعات.
وفخ تاني: لازم يكون عندك قياس صحيح للحمل. لو العدّاد بتاعك غلط، الاختيارين مش هينفعوا.
إمتى تستخدمه كافتراضي في 90% من الحالات. خصوصًا لما يكون عندك عدد كبير من السيرفرات أو أكتر من موزّع شغّال في نفس الوقت — لأنها بتتجنّب مشكلة «كل الموزّعات تختار نفس السيرفر الفاضي في نفس اللحظة» (اللي بتحصل مع Least Connections وبتسمّى Herd Behaviour).

الحدس بسيط: عشان طلبك يقع على سيرفر مزحوم في العشوائي البحت، محتاج صدفة واحدة (احتمالها p).
في الاختيارين، محتاج الاتنين يكونوا مزحومين — احتمالها p × p = p².
لو احتمال الزحمة 10%، احتمال الاتنين مزحومين 1% بس. تربيع احتمال صغير بيخلّيه شبه معدوم.
وزيادة لتلات اختيارات؟ بتحسّن كمان بس بشكل ضئيل — عشان كده وقفوا عند اتنين.
الخلاصة اللي تفضل معاك: خيار واحد = عشوائية كاملة وحمل غير متوازن. خياران = توازن قريب من المثالي بتكلفة شبه معدومة. تلاتة = تحسّن ضئيل مش مستاهل. عشان كده دي السياسة الافتراضية في YARP.

تمرين 3 — اختار الخوارزميةمتوسط

لكل حالة، اختار الخوارزمية واشرح السبب:

  1. خدمة gRPC باتصالات طويلة العمر بين خدماتك الداخلية.
  2. أسطول فيه 3 ماكينات قديمة (8 نوى) و7 ماكينات جديدة (32 نواة).
  3. خدمة WebSocket للإشعارات — العميل لازم يفضل على نفس العقدة.
  4. API عام فيه 200 سيرفر وطلبات متفاوتة جدًا.
شوف الحل
  • 1 → Least Connections (أو Two Choices على مستوى الطلب مش الاتصال). السبب: مع gRPC الاتصال بيتفتح مرة ويفضل — فالـ Round Robin هيوزّع الاتصالات مرة واحدة وخلاص وبعدين الحمل هيبقى عشوائي تمامًا. لازم توزيع على مستوى الطلب.
  • 2 → Weighted بأوزان 1 للقديم و4 للجديد — ونحطّها في مكان واحد موثّق مع تاريخ المراجعة. البديل الأفضل لو متاح: Two Choices اللي بيتعامل مع التباين تلقائيًا من غير أوزان يدوية.
  • 3 → IP Hash أو الأدق: تجزئة على معرّف المستخدم. هنا الالتصاق متطلب وظيفي مش راحة — الاتصال المفتوح موجود على عقدة بعينها. وخلي بالك من إعادة التوزيع عند تغيير العدد ⇒ استخدم Consistent Hashing.
  • 4 → Two Choices. مع 200 سيرفر، أي خوارزمية O(n) بتبقى مكلّفة على كل طلب، والتنسيق بين موزّعات متعددة بيبقى مستحيل عمليًا.
الطريقة اللي تقرّر بيها دايمًا اسأل تلات أسئلة بالترتيب: (1) الطلبات متجانسة في التكلفة؟ لو لأ ⇒ محتاج خوارزمية بتبص على الحالة. (2) الاتصالات قصيرة ولا طويلة؟ لو طويلة ⇒ التوزيع لازم يكون على مستوى الطلب. (3) فيه سبب وظيفي يخلّي العميل يلزم سيرفر معيّن؟ لو أيوه بس ⇒ تجزئة. غير كده، ابعد عن الالتصاق.

عندك 5 سيرفرات وLeast Connections. سيرفر رقم 3 اتعمله نشر غلط فبقى بيرجّع HTTP 500 في 2ms، والباقي بيردّوا صح في 200ms.

شوف الحل
// عدد الاتصالات الجارية على كل سيرفر (تقريبي) سيرفر سليم = RPS × 0.200s = حمل ظاهر عالي سيرفر 3 = RPS × 0.002s = حمل ظاهر ≈ صفر النتيجة → الموزّع يبعتله ~100% من الترافيك

خلال ثواني، سيرفر 3 بقى «الأقل اتصالات» دايمًا لأنه بيخلص فورًا. الموزّع — وهو بيحاول يبقى ذكي — حوّل عطل في 20% من الأسطول لانقطاع 100%. وده اسمه Black Hole أو Death Star.

  • فحص صحة سلبي: راقب نسبة أكواد 5xx لكل سيرفر، واشيله لو عدّت 10% على نافذة 30 ثانية. ده أسرع رد فعل ممكن لأنه بيستخدم الترافيك الحقيقي.
  • فحص صحة نشط أعمق: نقطة /health/ready بتتأكد من الاعتماديات فعليًا، مش بترجّع 200 على طول.
  • Circuit Breaker على مستوى الوجهة: افصل السيرفر مؤقتًا بعد سلسلة أخطاء وجرّبه تاني بعد فترة.
  • Two Choices بدل Least Connections: بتخفّف الأثر لأن السيرفر المعطوب لازم يتقابل مع سيرفر تاني في القرعة — فمش هياخد كل الترافيك، هياخد جزء منه.
الدرس المستفاد أي خوارزمية بتكافئ «السرعة» بتكافئ «الفشل السريع» كمان — لأن الفشل أسرع حاجة ممكن يعملها سيرفر. فأي مقياس سرعة لازم يتقرن بمقياس نجاح، وإلا هيشتغل ضدّك بالظبط في وقت الأزمة.

  • إيه الفرق العملي بين L4 وL7، وإيه اللي كل واحد شايفه؟
  • ليه الـ TLS Termination بيوفّر معالج، وإيه الخطر الأمني اللي بيجيبه؟
  • ليه Round Robin ممكن يبقى ظالم رغم إنه «عادل»؟
  • إيه سبب مشكلة Black Hole في Least Connections؟
  • ليه اختيارين عشوائيين بيدّوا نتيجة قريبة من فحص الأسطول كله؟
  • إمتى الـ IP Hash يكون قرار صح، وإمتى يكون كارثة؟

المفهوم 11

Health Checks — السؤال اللي بيتسأل كل ثانيتين

أهم مكوّن في التوسّع الأفقي، وأكتر واحد بيتكتب غلط.

Health Check فحص الصحة
التعريف الدقيق آلية بيعرف بيها الموزّع (أو المنسّق زي Kubernetes) إن نسخة معيّنة قادرة تخدم الطلبات دلوقتي ولا لأ — عشان يشيلها من الدورة قبل ما المستخدمين يحسّوا.
تشبيه 🏥 مدير الوردية بيمرّ على الموظفين كل شوية: «انت قادر تستقبل زباين؟».
مش بيسأل «انت عايش؟» — ده سؤال تافه. بيسأل «انت قادر تشتغل؟». والفرق بين السؤالين هو كل الموضوع في السلايد دي.
نشط مقابل سلبي Active Health Check: الموزّع بيبعت طلب مخصّص (GET /health/ready) كل 2–10 ثانية. بيكتشف المشاكل حتى لو مفيش ترافيك، بس بيضيف حمل وبيكتشف متأخر شوية.
Passive Health Check: الموزّع بيراقب الترافيك الحقيقي: نسبة أخطاء 5xx، وحالات الـ Timeout، ورفض الاتصال. بيكتشف فورًا وبدون تكلفة، بس محتاج ترافيك عشان يشتغل.
الصح: الاتنين مع بعض. النشط بيكتشف السيرفر اللي مات وهو ساكت، والسلبي بيكتشف السيرفر اللي «بيقول أنا كويس» وهو بيفشل.
فخ شائع ⚠️ فحص صحة بيرجّع 200 OK من غير ما يفحص أي حاجة — فبيفضل يقول «كويس» والتطبيق مش قادر يوصل لقاعدة البيانات.
والفخ العكسي أخطر بكتير: فحص بيفحص كل الاعتماديات، فلو خدمة تانية وقعت ⇒ كل نسخك بتبان مريضة ⇒ اتشالت كلها ⇒ انقطاع كامل بدل تدهور جزئي. وده الجزء الجاي.
إمتى تستخدم إيه القاعدة: افحص بس الاعتماديات اللي من غيرها الخدمة عديمة الفايدة تمامًا. قاعدة البيانات الأساسية؟ أيوه. خدمة التوصيات الاختيارية؟ لأ — دي تتحوّل لتدهور رشيق مش لفشل.

Liveness «العملية دي لسه عايشة ولا اتعلّقت؟» إعادة تشغيل النسخة (restart) يرجّع 200 على طول — من غير أي فحص خارجي

Startup «خلّصت الإقلاع الأولي؟» استنّى — وأوقف الفحصين التانيين لحد ما ينجح تحميل الكاش الأولي + JIT warmup

ثلاث أرقام صغيرة بتحدّد الفرق بين نظام بيتعافى ونظام بيتقتل نفسه
livenessProbe
مجسّ الحياة. المنسّق بينادي المسار ده بشكل دوري. لو فشل ⇒ بيقتل الحاوية ويشغّلها من جديد.
ولذلك ما ينفعش أبدًا يفحص حاجة برّه العملية نفسها.
periodSeconds: 10
كل 10 ثواني بيسأل. أقل من كده = حمل زيادة، أكتر من كده = اكتشاف متأخر.
failureThreshold: 3
3 فشل متتالي قبل ما ياخد إجراء. الرقم ده هو حزام الأمان ضد الإيجابيات الكاذبة: تأخير شبكة لحظي واحد ما يقتلش النسخة.
الزمن الكلي للاكتشاف = 10 × 3 = 30 ثانية.
timeoutSeconds: 1
ثانية واحدة مهلة لكل محاولة. لو الرد ما جاش خلالها تُحسب فشل.
فخ خطير: لو خلّيتها كبيرة (5 ثواني مثلاً) والفحص بيلمس قاعدة البيانات، ساعة الضغط كل الفحوصات هتتأخر وتفشل مع بعض ⇒ إعادة تشغيل جماعي في أسوأ لحظة ممكنة.
السطر ده معناه: «اسأل كل 10 ثواني، بمهلة ثانية، ولو فشل 3 مرات ورا بعض اقتل النسخة وشغّلها من جديد». يعني أقصى وقت لاكتشاف نسخة متعلّقة = 30 ثانية.

إزاي 4 أسطر في فحص الصحة وقّعوا المنصة بالكامل

القصة دي بتتكرر في كل شركة تقريبًا. اقراها كويس عشان ما تعيدهاش.

مثال محلول 3: من تدهور 3% لانقطاع 100% في 40 ثانية

الإعداد: منصة تجارة إلكترونية، 40 نسخة من خدمة الكتالوج على Kubernetes. الـ readinessProbe بينادي /health اللي بيفحص: قاعدة البيانات + Redis + خدمة التوصيات + خدمة المخزون.

  1. التوقيت 00:00 — خدمة التوصيات بتبطّأ

    نشر جديد فيه استعلام مش مفهرس. زمن ردها طلع من 30ms لـ 4 ثواني. تأثيرها الحقيقي على المستخدم: شريط «قد يعجبك» مش بيظهر — يعني 3% من قيمة الصفحة.

  2. 00:12 — الفحص بدأ يفشل

    الـ /health عنده timeoutSeconds: 2، وخدمة التوصيات بتاخد 4 ثواني ⇒ الفحص بيفشل. مش على نسخة واحدة — على 40 نسخة في نفس اللحظة، لأنهم كلهم بيفحصوا نفس الخدمة المريضة.

  3. 00:36 — الإزالة الجماعية

    failureThreshold: 3 اكتمل. المنسّق شال الـ 40 نسخة من الـ Endpoints. عدد النسخ الجاهزة بقى صفر. الموزّع مالوش وجهة ⇒ كل الطلبات بترجع 503.

  4. 00:40 — الحلقة اتقفلت

    الخدمة كلها واقعة. المستخدمون بيعيدوا التحميل ⇒ ضغط أعلى ⇒ لما نسخة تحاول ترجع بتلاقي موجة طلبات مستنية بتوقعها تاني. والأهم: خدمة التوصيات نفسها ما كانتش واقعة أصلاً — كانت بطيئة بس.

التقسيم بالوسوم (tags) هو المفتاح — نقطة واحدة لكل نوع.

Program.csC# / .NET 9
// ═══ 1) تسجيل الفحوصات مع وسم لكل نوع ═══
builder.Services.AddHealthChecks()
    // liveness: مفيش أي فحص خارجي — بس بيثبت إن العملية بترد
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])

    // readiness: الاعتماديات الحرجة بس — اللي من غيرها الخدمة بلا فايدة
    .AddSqlServer(sqlConn, name: "sql", tags: ["ready"],
        failureStatus: HealthStatus.Unhealthy,
        timeout: TimeSpan.FromSeconds(2))

    // Redis اختياري ⇒ Degraded مش Unhealthy ⇒ النسخة ما تتشالش
    .AddRedis(redisConn, name: "redis", tags: ["ready"],
        failureStatus: HealthStatus.Degraded)

    // startup: بيتأكد إن الكاش الأولي اتحمّل قبل استقبال أي ترافيك
    .AddCheck<WarmupHealthCheck>("warmup", tags: ["startup"]);

// ═══ 2) تخزين نتيجة الفحص 5 ثواني (يمنع ضرب الاعتماديات مع كل مجسّ) ═══
builder.Services.Configure<HealthCheckPublisherOptions>(o =>
{
    o.Delay = TimeSpan.FromSeconds(5);
    o.Period = TimeSpan.FromSeconds(5);
});

var app = builder.Build();

// ═══ 3) نقطة لكل نوع — والفلترة بالوسم ═══
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready"),
    // Degraded تعتبر نجاح ⇒ النسخة تفضل في الموزّع
    ResultStatusCodes =
    {
        [HealthStatus.Healthy]   = StatusCodes.Status200OK,
        [HealthStatus.Degraded]  = StatusCodes.Status200OK,
        [HealthStatus.Unhealthy] = StatusCodes.Status503ServiceUnavailable
    }
});

app.MapHealthChecks("/health/startup", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("startup")
});
الكود ده بيعمل إيه سطر سطر 1. AddCheck("self", … tags: ["live"]) — فحص بيرجّع «سليم» على طول. الغرض منه إثبات إن الـ Thread Pool مش متعلّق والعملية بترد. لو ده فشل، إعادة التشغيل فعلاً هي الحل الصح.
2. AddSqlServer(… timeout: 2s) — المهلة هنا حرجة: من غيرها، ضغط على قاعدة البيانات هيخلّي الفحص يستنى للأبد وييجي عليه مهلة المجسّ.
3. failureStatus: HealthStatus.Degraded لـ Redis — دي أهم سطر في الملف. معناها: «لو Redis وقع، سجّل ده وقول للمراقبة، بس ما تشلّش النسخة».
4. HealthCheckPublisherOptions — بينشر النتيجة كل 5 ثواني بدل ما كل مجسّ يعمل استعلام جديد. مع 40 نسخة ومجسّ كل 10 ثواني، ده بيفرق بين 4 استعلامات/ثانية و240.
5. ResultStatusCodes — بنقول صراحة إن Degraded ترجع 200. الافتراضي في .NET إنها ترجع 200 فعلاً، بس كتابتها صراحة بتمنع أي التباس وبتوضّح النية لأي حد يقرا الكود بعدك.

المفهوم 12

Stateless — الشرط اللي من غيره مفيش توسّع أفقي

أي بايت حالة بتخزّنه في ذاكرة السيرفر بيربط المستخدم بالسيرفر ده — وبيكسر كل حاجة بعد كده.

Stateless Service خدمة عديمة الحالة
التعريف الدقيق خدمة أي نسخة فيها تقدر تخدم أي طلب، لأن كل المعلومات المطلوبة إما جاية مع الطلب نفسه (توكن، معرّفات) أو من مخزن مشترك (قاعدة بيانات، Redis).
مهم: Stateless مش معناها «مفيش حالة» — معناها الحالة مش عايشة في ذاكرة النسخة.
تشبيه ☕ كافيه فيه 5 كاشيرات. لو الكاشير كتب طلبك على ورقة في جيبه، لازم ترجع له هو بالذات — ولو خرج، طلبك ضاع.
ولو كتبه في النظام المشترك، أي كاشير يقدر يكمّل معاك، ولو واحد مشي محدش يحس.
«الورقة في الجيب» = الحالة في الذاكرة.
الحالة بتروح فين بدل الذاكرة؟
  • جلسة المستخدم ⇒ Distributed Cache (Redis) أو توكن موقّع (JWT) عند العميل.
  • كاش البيانات ⇒ Redis، أو HybridCache (كاش محلي + موزّع مع إبطال).
  • الملفات المرفوعة ⇒ Object Storage (S3 / Azure Blob) مش قرص السيرفر.
  • مفاتيح تشفير الكوكيز ⇒ Data Protection مخزّنة في Redis أو قاعدة بيانات.
  • المهام المجدولة ⇒ قفل موزّع أو خدمة جدولة، مش Timer في كل نسخة.
  • حالة اتصال WebSocket ⇒ SignalR Backplane على Redis.
فخ شائع ⚠️ — الحالة المخفية الحاجات دي كلها حالة في الذاكرة والناس ما بتحسبهاش:
• static Dictionary أو static List فيه بيانات.
• IMemoryCache لبيانات لازم تكون موحّدة (أسعار، صلاحيات).
• عدّاد Rate Limit في الذاكرة ⇒ مع 10 نسخ، الحد الفعلي بقى 10 أضعاف!
• رفع ملف على Path.GetTempPath() وقراءته في طلب تاني.
• BackgroundService بيشتغل في كل نسخة ⇒ المهمة بتتنفّذ 10 مرات.
إمتى تستخدمه دايمًا، من أول سطر. التكلفة وانت بتبني صفر تقريبًا، وتكلفة التحويل بعدين شهور. حتى لو شغّال على ماكينة واحدة — اكتبها Stateless وسيبها ماكينة واحدة.
المفهوم 13

Session Affinity — الحل السهل اللي بيرجع يعضّك

لما تكتشف إن خدمتك مش Stateless، فيه إغراء إنك «تلزّق» المستخدم بسيرفر. خلينا نشوف التمن.

Session Affinity / Sticky Sessions التصاق الجلسة
التعريف الدقيق إعداد في الموزّع بيخلّي كل طلبات نفس المستخدم تروح لنفس النسخة، عن طريق كوكي بيكتبه الموزّع (Set-Cookie: .Yarp.Affinity=srv-3) أو تجزئة على عنوان العميل.
تشبيه ☕ رجعنا لكافيه الأوراق في الجيوب: بدل ما نصلّح النظام، حطّينا حارس على الباب بيقولّك «انت بتاع الكاشير رقم 3، متقفش عند حد تاني».
شغّال… لحد ما الكاشير رقم 3 ياخد إجازة.
تطبيق .NET في YARP: SessionAffinity: { Enabled: true, Policy: "Cookie", FailurePolicy: "Redistribute" }.
الـ FailurePolicy مهمة: Redistribute معناها «لو السيرفر الملزوق راح، وزّع من جديد» — أحسن بكتير من Return503.
ليه ده فخ ⚠️ (خمس مشاكل) 1) الحمل بيبقى غير متوازن ومستحيل تصلّحه. لو سيرفر مسك 3 عملاء كبار، هيفضل مخنوق وانت ما تقدرش تنقلهم.
2) التوسّع الجديد بيبقى بلا فايدة. ضفت 5 سيرفرات وقت الذروة؟ الجلسات القديمة كلها ملزوقة بالقديم — السيرفرات الجديدة هتقعد فاضية.
3) النشر بيبقى مؤلم. كل نسخة بتتقفل = مجموعة مستخدمين بيفقدوا جلستهم (سلة اتمسحت، فورم ضاع).
4) الفشل بيبقى مرئي للمستخدم. فايدة النسخ المتعددة إن العطل يبقى شفاف — الالتصاق بيلغي دي بالظبط.
5) بيخفي المشكلة الحقيقية. الخدمة فضلت Stateful، والمشكلة اتأجّلت لحد ما تبقى أصعب.
إمتى يكون مقبول فعلاً حالتين بس:
(أ) اتصال طويل العمر بطبيعته: WebSocket / SignalR — الاتصال فيزيائيًا موجود على عقدة واحدة.
(ب) كحل مؤقت معلن أثناء ترحيل تطبيق قديم، مع تاريخ انتهاء مكتوب ومهمة في الـ backlog لإزالته.
وما عدا كده: الحل الصح إنك تنقل الحالة لمخزن مشترك — والسلايد الجاية بتوريك إزاي.

إزاي تخلّي خدمتك Stateless فعليًا

أربع نقلات: الكاش، ومفاتيح الحماية، والجلسة، والقفل الموزّع.

Program.csC# / .NET 9
var builder = WebApplication.CreateBuilder(args);
var redisConn = builder.Configuration.GetConnectionString("Redis")!;

// ═══ 1) كاش موزّع بدل IMemoryCache للبيانات المشتركة ═══
builder.Services.AddStackExchangeRedisCache(o =>
{
    o.Configuration = redisConn;
    o.InstanceName  = "shop:";   // بادئة تفصل تطبيقك عن غيره
});

// HybridCache (.NET 9): كاش محلي سريع + موزّع + حماية من انهيار الكاش
builder.Services.AddHybridCache(o =>
{
    o.DefaultEntryOptions = new()
    {
        LocalCacheExpiration = TimeSpan.FromSeconds(20), // نسخة محلية قصيرة
        Expiration           = TimeSpan.FromMinutes(10)  // النسخة المشتركة
    };
});

// ═══ 2) مفاتيح الحماية في مخزن مشترك — أهم سطر في الملف ═══
var mux = await ConnectionMultiplexer.ConnectAsync(redisConn);
builder.Services.AddDataProtection()
    .PersistKeysToStackExchangeRedis(mux, "shop:dp-keys")
    .SetApplicationName("shop")          // لازم نفس الاسم في كل النسخ
    .SetDefaultKeyLifetime(TimeSpan.FromDays(90));

// ═══ 3) الجلسة في Redis (لو مضطر تستخدم Session أصلاً) ═══
builder.Services.AddSession(o =>
{
    o.IdleTimeout = TimeSpan.FromMinutes(30);
    o.Cookie.HttpOnly = true;
    o.Cookie.IsEssential = true;
});

var app = builder.Build();

// ═══ 4) قراءة بالكاش الموزّع — أي نسخة هتشوف نفس النتيجة ═══
app.MapGet("/products/{id:int}", async (int id,
    HybridCache cache, IProductRepo repo, CancellationToken ct) =>
{
    // GetOrCreateAsync بيعمل قفل داخلي ⇒ طلب واحد بس بيروح للـ DB
    // حتى لو 500 طلب جم في نفس اللحظة على مفتاح مش موجود
    return await cache.GetOrCreateAsync(
        $"product:{id}",
        async token => await repo.GetAsync(id, token),
        cancellationToken: ct);
});

// ═══ 5) مهمة مجدولة تشتغل في نسخة واحدة بس (قفل موزّع) ═══
app.MapPost("/jobs/settle", async (IConnectionMultiplexer redis) =>
{
    var db = redis.GetDatabase();
    // SET key value NX EX 60 — بينجح مع أول نسخة بس
    bool gotLock = await db.StringSetAsync(
        "lock:settle", Environment.MachineName,
        TimeSpan.FromSeconds(60), When.NotExists);

    if (!gotLock) return Results.Ok("نسخة تانية شغّالة عليها");
    // … نفّذ المهمة هنا …
    return Results.Ok("تم");
});
الكود ده بيعمل إيه سطر سطر 1. AddStackExchangeRedisCache بيسجّل IDistributedCache على Redis. الفرق عن IMemoryCache إن النتيجة مشتركة — نسخة كتبت، كل النسخ بتقرا.
2. AddHybridCache بيدمج الاتنين: بيقرا من الذاكرة المحلية (نانو ثانية) وبيرجع للموزّع لو مش موجود. وGetOrCreateAsync بيعمل Stampede Protection: لو 500 طلب طلبوا مفتاح منتهي في نفس اللحظة، واحد بس بيروح لقاعدة البيانات والباقي بيستنى نتيجته.
3. PersistKeysToStackExchangeRedis — من غير السطر ده، كل نسخة بتولّد مفاتيح تشفير خاصة بيها، فالكوكي اللي اتعمل على نسخة 1 مش هيتفك على نسخة 2 ⇒ المستخدم بيتسجّل خروجه عشوائيًا. ده أشهر عرض لخدمة مش Stateless في .NET.
4. SetApplicationName لازم يبقى نفس النص في كل النسخ — لأنه بيدخل في اشتقاق المفتاح. اختلافه بيلغي فايدة الخطوة اللي قبلها.

Service Discovery — مين عارف عناوين مين؟

لما النسخ بتظهر وتختفي كل دقيقة، ما ينفعش حد يكتب العناوين في ملف إعدادات.

Service Discovery اكتشاف الخدمات
التعريف الدقيق آلية بتخلّي الخدمة تلاقي عناوين النسخ السليمة لخدمة تانية وقت التشغيل، بدل ما تكون العناوين مكتوبة في الإعدادات.
بتشتغل على مرحلتين: تسجيل (النسخة بتقول «أنا موجودة على العنوان ده») واستعلام (خدمة بتسأل «فين نسخ خدمة الفواتير؟»).
تشبيه 📞 دليل التليفونات. من غيره لازم تحفظ رقم كل واحد وتحدّثه يدويًا كل ما حد يغيّر رقمه.
والفرق هنا إن «الأرقام» بتتغيّر كل دقيقة — كل نشر أو توسّع تلقائي بيخلق عناوين جديدة ويلغي قديمة.
الأربع طرق — وفرقهم العملي
  • Client-side Discovery: العميل بيسأل السجل بنفسه وبيختار النسخة وبيوزّع بنفسه. أسرع (مفيش قفزة زيادة) وأذكى، بس بيحط منطق التوزيع في كل خدمة وكل لغة.
  • Server-side Discovery: العميل بيكلّم عنوان ثابت (موزّع/بروكسي) والموزّع هو اللي بيعرف. أبسط بكتير للعملاء، بس بيضيف قفزة شبكة ونقطة إدارة.
  • Registry-based (Consul, etcd, Eureka): سجل مركزي، النسخ بتسجّل نفسها وبتبعت نبضة (heartbeat). بيدّي بيانات غنية (أوزان، وسوم، صحة) وتحديث شبه لحظي.
  • DNS-based: اسم بيرجّع مجموعة عناوين. أبسط حاجة ممكنة وشغّالة في كل مكان — بس الـ TTL هو عدوّك: النسخة تموت والعملاء لسه بيكلّموها لحد ما الكاش ينتهي. وبعض المكتبات بتكاش الـ DNS للأبد!
فخ شائع ⚠️ في .NET تحديدًا HttpClient القديم كان بيكاش تحليل الـ DNS طول عمر الـ HttpMessageHandler — فلو الخدمة اتنقلت لعنوان جديد، تطبيقك يفضل يكلّم العنوان القديم لحد ما تعمل إعادة تشغيل.
الحل: استخدم IHttpClientFactory دايمًا (بيدوّر الـ handler كل دقيقتين افتراضيًا)، أو حدّد PooledConnectionLifetime على SocketsHttpHandler.
إمتى تستخدم إيه على Kubernetes: الـ Service بيعملها لك — اسم داخلي ثابت + توزيع L4 على النسخ الجاهزة بس. ده اكتشاف من ناحية السيرفر مبني على DNS، ومناسب لـ 90% من الحالات.
محتاج توزيع ذكي أو أوزان أو مناطق؟ روح لـ Consul أو شبكة خدمات (Service Mesh).
خدمتين بس؟ عنوان في الإعدادات كفاية — ما تعقّدش حياتك.

Circuit Breaker — قاطع الدائرة

فكرة مسروقة من الكهربا حرفيًا: بدل ما الحريق ينتشر، اقطع الدائرة بسرعة.

Circuit Breaker قاطع الدائرة
التعريف الدقيق مكوّن بيراقب نسبة فشل النداءات لخدمة معيّنة، ولما تعدّي عتبة معيّنة بيوقف إرسال أي طلبات ليها فورًا ويرجّع فشل سريع (Fail Fast) من غير ما يستنى المهلة. وبعد فترة بيسمح بعدد قليل من الطلبات التجريبية عشان يشوف رجعت ولا لأ.
تشبيه ⚡ القاطع في لوحة الكهربا. لما فيه تماس، هو ما بيحاولش «يعدّي الكهربا برضه» — بيفصل فورًا. لأن المحاولة المستمرة هتحرق البيت كله.
وبعد ما تصلّح، بترفع القاطع وتشوف: لو التماس لسه موجود بينزل تاني. ده بالظبط الـ Half-Open.
ليه «الفشل السريع» أفضل من «الانتظار»؟ لو خدمة وقعت وعندك مهلة 30 ثانية: كل طلب هيمسك Thread واتصال ومساحة في الطابور لمدة 30 ثانية قبل ما يفشل. عند 200 RPS ده معناه 6,000 طلب معلّق في أي لحظة ⇒ Thread Pool Starvation ⇒ خدمتك انت كمان وقعت رغم إن العطل في خدمة تانية.
مع القاطع: الطلب بيفشل في < 1ms، والموارد بتفضل متاحة لباقي الوظايف اللي شغّالة كويس.
فخ شائع ⚠️ قاطع واحد لكل الخدمات. لو عملت قاطع مشترك، عطل في خدمة التوصيات هيقفل النداءات لخدمة الدفع كمان.
الصح: قاطع منفصل لكل وجهة (وأحيانًا لكل نقطة نهاية لو سلوكها مختلف).
وفخ تاني: عتبة منخفضة أوي (10% مثلاً) بتخلّي القاطع يفتح من أي ارتفاع مؤقت، فيتحوّل هو نفسه لمصدر انقطاع.
إمتى تستخدمه على كل نداء شبكة خارج عمليتك: خدمة تانية، قاعدة بيانات بعيدة، بوابة دفع، أي API طرف تالت.
ما تستخدموش على عمليات محلية (قراءة ملف، حساب في الذاكرة) — مفيش فايدة، وبتضيف تعقيد بلا مقابل.

Cascading Failure — إزاي عطل صغير بيبلع النظام كله

ده العدو اللي كل أنماط الصمود اتعملت عشانه. لازم تشوف الميكانيكا بالأرقام.

Cascading Failure الفشل المتتالي
التعريف الدقيق فشل في مكوّن واحد بيستهلك موارد المكوّنات اللي بتعتمد عليه (خيوط، اتصالات، ذاكرة)، فتفشل هي كمان، فتوقّع اللي بيعتمد عليها — لحد ما النظام كله يقف.
الوقود الأساسي: الانتظار. كل طلب مستني بيمسك موارد.
تشبيه 🚗 حادثة في حارة واحدة على الدايري. العربيات وقفت، اللي وراهم وقفوا، الزحمة وصلت للمخرج اللي قبله، فالعربيات اللي داخلة من مخرج تاني وقفت كمان.
الحادثة اتحلّت في 5 دقايق — الزحمة فضلت ساعتين. ده بالظبط اللي بيحصل في الأنظمة: العطل بيخلص بسرعة، والأثر بيفضل.
المُضاعِفات اللي بتحوّل عطل لكارثة
  • مهل طويلة أو غير موجودة ⇒ الخيوط بتفضل ماسكة موارد لدقايق.
  • إعادة محاولة بدون تباطؤ ⇒ الحمل على الخدمة المريضة بيتضاعف 3 مرات في أسوأ لحظة (Retry Storm).
  • مجموعة اتصالات مشتركة ⇒ نقطة نهاية بطيئة بتستهلك الاتصالات المخصّصة لكل الباقي.
  • مفيش قاطع دائرة ⇒ بنفضل نبعت لخدمة معروف إنها فاشلة.
  • موجة العملاء ⇒ المستخدمون بيعيدوا التحميل، فالحمل بيتضاعف وقت الضعف.
الدفاعات الأربعة (بالترتيب ده) 1) Timeout — يمنع الانتظار اللانهائي (خط الدفاع الأول والأهم).
2) Circuit Breaker — يمنع الإرسال للمعطوب أصلاً.
3) Bulkhead — يحصر الضرر في جزء من الموارد.
4) Backpressure + Rate Limiting — يمنع دخول شغل أكتر من الطاقة.
مثال محلول 4: إزاي خدمة بطيئة بتوقّع خدمة سليمة — بالأرقام

خدمة الطلبات: 500 RPS · 200 خيط متاح · بتنادي خدمة المخزون اللي زمنها الطبيعي 50ms.

// ═══ الوضع الطبيعي — قانون ليتل ═══ الطلبات المتزامنة = RPS × زمن الرد = 500 × 0.05s = 25 خيط مشغول الاستغلال = 25 / 200 = 12.5% مرتاحين جدًا // ═══ خدمة المخزون بقت 5 ثواني (مش واقعة — بطيئة بس) ═══ الطلبات المتزامنة = 500 × 5s = 2,500 خيط مطلوب المتاح = 200 النتيجة → الطابور بيكبر بـ 460 طلب/ثانية بعد 10 ثواني → خدمة الطلبات وقعت بالكامل // ═══ نفس السيناريو مع مهلة 500ms ═══ الطلبات المتزامنة = 500 × 0.5s = 250 خيط مع Bulkhead بحد 50 → 50 خيط للمخزون فقط، 150 لباقي الوظايف النتيجة → صفحة المنتج شغّالة، المخزون بيعرض "غير متاح"
الرقم اللي يفضل معاك من السلايد دي خدمة المخزون ما وقعتش — بقت أبطأ 100 مرة بس. ومع ذلك في الحالة الأولى وقّعت خدمة سليمة تمامًا خلال 10 ثواني.
البطء أخطر من الفشل. الفشل بيرجّع الموارد فورًا، والبطء بياخدها رهينة.
ولاحظ إن الفرق بين «انهيار كامل» و«تدهور جزئي مقبول» كان سطرين إعدادات: مهلة + حاجز.

Bulkhead و Timeout — أرخص حمايتين موجودين

Bulkhead الحاجز المانع للغرق
التعريف الدقيق تقسيم الموارد (خيوط، اتصالات، ذاكرة) لـ حجرات منفصلة، كل حجرة مخصّصة لوظيفة أو وجهة معيّنة وليها سقف ثابت. لو حجرة اتملت، اللي بعدها بيترفض فورًا — من غير ما يأثر على باقي الحجرات.
تشبيه 🚢 هيكل السفينة متقسّم لحجرات مغلقة. لو حجرة اتخرمت واتملت مياه، السفينة بتفقد جزء من طفوها — مش بتغرق.
الاسم جاي من ده حرفيًا. من غير الحجرات دي، أي خرم في أي مكان = غرق كامل.
تطبيق .NET ResiliencePipelineBuilder.AddConcurrencyLimiter(50, queueLimit: 10) — يعني 50 نداء متزامن كحد أقصى لهذه الوجهة، و10 في الانتظار، والباقي يترفض فورًا.
وعلى مستوى الشبكة: SocketsHttpHandler.MaxConnectionsPerServer بيعمل نفس الحاجز على مستوى الاتصالات.
وعلى مستوى قاعدة البيانات: Max Pool Size منفصل لكل سياق (سياق للقراءة وسياق للتقارير) بيمنع تقرير تقيل من استهلاك كل الاتصالات.
فخ شائع ⚠️ حجرات صغيرة أوي ⇒ بترفض طلبات وانت عندك موارد فاضية في حجرات تانية (استغلال ضعيف). وحجرات كبيرة أوي ⇒ مفيش عزل حقيقي.
الطريقة الصح للتحجيم: ابدأ من قانون ليتل: الحد = RPS المتوقّع × زمن الرد المستهدف × 1.5.
وفخ تاني: لو حطيت طابور انتظار كبير ورا الحاجز، رجّعت مشكلة الانتظار من الباب — خلّي الطابور صغير.
إمتى تستخدمه لما تكون خدمة واحدة بتنادي أكتر من اعتمادية بأهميات مختلفة. الحالة الكلاسيكية: نقطة نهاية التقارير (بطيئة، أهميتها أقل) ونقطة نهاية الدفع (سريعة، حرجة) في نفس التطبيق. من غير حاجز، التقارير هتاكل كل الخيوط وقت الضغط والدفع هيقف.
Timeout المهلة
التعريف الدقيق الحد الأقصى للوقت اللي هتستنّاه لعملية قبل ما تعتبرها فاشلة وترجّع مواردها.
أي نداء شبكة من غير مهلة صريحة = قنبلة موقوتة، لأن الافتراضي غالبًا 100 ثانية أو لا نهائي.

Retry with Exponential Backoff + Jitter إعادة المحاولة بتباطؤ أسّي وعشوائية
التعريف الدقيق إعادة إرسال الطلب الفاشل، بشرط إن الفاصل بين المحاولات يتضاعف كل مرة (تباطؤ أسّي)، ويتضاف عليه رقم عشوائي (jitter) عشان العملاء ما يعيدوش كلهم في نفس اللحظة.
تشبيه 📞 الخط مشغول. الشخص العاقل بيعيد بعد دقيقة، وبعدين بعد دقيقتين، وبعدين بعد أربعة.
والشخص اللي بيعيد كل ثانية هو نفسه سبب إن الخط فضل مشغول.
والـ jitter؟ تخيّل 10 آلاف شخص كلهم بيعيدوا بعد دقيقة بالظبط — هيعملوا موجة تانية بنفس القوة. العشوائية بتفرّشهم على الوقت.
فخ شائع ⚠️ — إعادة اللي مش المفروض يتعاد ما تعيدش أبدًا:
• أخطاء 4xx (طلبك غلط — الإعادة هتفشل بنفس الشكل).
• عمليات مش Idempotent من غير مفتاح تفرّد: إعادة POST /payments ممكن تخصم مرتين!
• لما تكون المهلة الكلية خلصت أصلاً.
أخطر فخ: الإعادة المتداخلة. A بتعيد 3 مرات، وكل واحدة B بتعيد 3 مرات، وكل واحدة C بتعيد 3 ⇒ 27 نداء على خدمة واقعة أصلاً. القاعدة: أعد المحاولة في طبقة واحدة بس — الأقرب للمستخدم عادةً.
إمتى تستخدمه للأعطال العابرة بس: انقطاع شبكة لحظي، 503، 429 (مع احترام ترويسة Retry-After)، deadlock في قاعدة البيانات.
وخلّي عدد المحاولات 2 أو 3 بحد أقصى — أكتر من كده بيضيف حمل أكتر مما بينقذ.
// ═══ الصيغة الأساسية ═══ delay = base × 2^n ± jitter // ═══ التطبيق: base = 200ms ═══ n = 0 → 200 × 1 = 200 ms n = 1 → 200 × 2 = 400 ms n = 2 → 200 × 4 = 800 ms n = 3 → 200 × 8 = 1,600 ms // ═══ Full Jitter — الصيغة اللي الأبحاث أثبتت إنها الأفضل ═══ sleep = random(0, base × 2^n) n = 2 → أي رقم عشوائي بين 0 و 800 ms
delay = base × 2^n ± jitter
أربع رموز — كل واحد بيحل مشكلة مختلفة
delay
مدة الانتظار قبل المحاولة الجاية. مش وقت التنفيذ — وقت السكوت.
base
الفاصل الأساسي — نقطة البداية. عادة 100–500ms.
اختياره مش عشوائي: لازم يكون أطول من زمن التعافي من عطل لحظي (تغيير مسار شبكة مثلاً بياخد عشرات المللي ثانية) وأقصر من صبر المستخدم.
2^n
2 أُس n — «اتنين مرفوعة للأس n». n هو رقم المحاولة (بيبدأ من صفر).
القيم: 2⁰=1, 2¹=2, 2²=4, 2³=8.
ليه أسّي مش خطّي؟ لأن التباطؤ الخطّي (200، 400، 600) بيزوّد بطيء أوي — لو الخدمة محتاجة 30 ثانية تقوم، هتكون ضربتها 50 مرة قبلها. الأسّي بيوصل لثواني في 4-5 محاولات بس.
± jitter
عشوائية مضافة. ودي أهم جزء وأكتر جزء الناس بتشيله عشان «مش مهم».
المشكلة اللي بتحلها: لو 5000 عميل فشلوا في نفس اللحظة (خدمة وقعت)، كلهم هيعيدوا بعد 200ms بالظبط، وبعدين بعد 400ms بالظبط… يعني موجات متزامنة بتضرب الخدمة وهي بتحاول تقوم. ده اسمه Thundering Herd.
مع العشوائية، الـ 5000 بيتفرشوا على الفترة كلها ⇒ الحمل بيبقى منبسط والخدمة تلحق تقوم.
Full Jitter
بدل ما تضيف عشوائية صغيرة، خلّي المدة كلها عشوائية بين صفر والحد الأسّي.
الأبحاث التطبيقية أثبتت إنها بتقلّل العدد الكلي للمحاولات وبتقلّل زمن الإنجاز في نفس الوقت — يعني أفضل في الاتجاهين مش مقايضة.
الصيغة بتقول: «استنّى مدة بتتضاعف كل محاولة (عشان تدّي الخدمة فرصة تقوم)، وخلّي المدة عشوائية (عشان كل العملاء ما يرجعوش في نفس اللحظة)». الجزء الأسّي بيحمي الخدمة، وجزء العشوائية بيحمي من نفسك لما تكون كتير.

// ═══ (أ) الطريقة الجاهزة — 5 أنماط دفعة واحدة ═══
builder.Services.AddHttpClient<InventoryClient>(c =>
{
    c.BaseAddress = new("https://inventory.internal/");
})
.AddStandardResilienceHandler(o =>
{
    // الترتيب الفعلي: RateLimiter → TotalTimeout → Retry → CircuitBreaker → AttemptTimeout
    o.TotalRequestTimeout.Timeout   = TimeSpan.FromSeconds(5);  // سقف كل المحاولات
    o.AttemptTimeout.Timeout        = TimeSpan.FromSeconds(2);  // مهلة المحاولة الواحدة

    o.Retry.MaxRetryAttempts        = 3;
    o.Retry.BackoffType             = DelayBackoffType.Exponential;
    o.Retry.Delay                   = TimeSpan.FromMilliseconds(200);
    o.Retry.UseJitter               = true;   // ← يمنع Thundering Herd

    o.CircuitBreaker.FailureRatio   = 0.5;
    o.CircuitBreaker.MinimumThroughput = 20;
    o.CircuitBreaker.SamplingDuration  = TimeSpan.FromSeconds(30);
    o.CircuitBreaker.BreakDuration     = TimeSpan.FromSeconds(15);
});

// ═══ (ب) خط صريح لما تحتاج تحكّم كامل ═══
builder.Services.AddResiliencePipeline<string, HttpResponseMessage>(
    "payments", (pipeline, ctx) =>
{
    pipeline
        // 1) حاجز: 50 نداء متزامن كحد أقصى + 10 في الانتظار
        .AddConcurrencyLimiter(permitLimit: 50, queueLimit: 10)

        // 2) مهلة كلية لكل العملية
        .AddTimeout(TimeSpan.FromSeconds(4))

        // 3) إعادة محاولة بتباطؤ أسّي + عشوائية
        .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
        {
            MaxRetryAttempts = 2,
            BackoffType      = DelayBackoffType.Exponential,
            Delay            = TimeSpan.FromMilliseconds(250),
            UseJitter        = true,
            // نعيد بس على الأخطاء العابرة — مش على 4xx ولا على النجاح
            ShouldHandle = new PredicateBuilder<HttpResponseMessage>()
                .HandleResult(r => r.StatusCode == HttpStatusCode.ServiceUnavailable)
                .HandleResult(r => r.StatusCode == HttpStatusCode.TooManyRequests)
                .Handle<HttpRequestException>()
                .Handle<TimeoutRejectedException>(),
            // نحترم Retry-After اللي الخدمة بعتته لو موجود
            DelayGenerator = static args =>
            {
                var after = args.Outcome.Result?.Headers.RetryAfter?.Delta;
                return new ValueTask<TimeSpan?>(after);
            }
        })

        // 4) قاطع الدائرة — آخر خط قبل الخروج للشبكة
        .AddCircuitBreaker(new CircuitBreakerStrategyOptions<HttpResponseMessage>
        {
            FailureRatio       = 0.5,
            MinimumThroughput  = 20,
            SamplingDuration   = TimeSpan.FromSeconds(30),
            BreakDuration      = TimeSpan.FromSeconds(15),
            OnOpened = args =>
            {
                Log.Warning("القاطع اتفتح لمدة {D}", args.BreakDuration);
                return ValueTask.CompletedTask;
            }
        })

        // 5) بديل: بدل ما نرمي استثناء، نرجّع رد متدهور
        .AddFallback(new FallbackStrategyOptions<HttpResponseMessage>
        {
            FallbackAction = _ => Outcome.FromResultAsValueTask(
                new HttpResponseMessage(HttpStatusCode.OK)
                {
                    Content = new StringContent("""{"available":null,"stale":true}""")
                })
        });
});

2. مهلتين مش واحدة. AttemptTimeout للمحاولة الواحدة (2s) وTotalRequestTimeout للعملية كلها بمحاولاتها (5s). من غير الكلية، 3 محاولات × 2 ثانية + فترات الانتظار = المستخدم ممكن يستنى 8 ثواني.
3. ShouldHandle هي خط الدفاع ضد الإعادة الخاطئة. لاحظ إننا بنعيد على 503 و429 والاستثناءات العابرة بس — مفيش 400 ولا 404، لأن إعادتهم فشل مضمون.
4. DelayGenerator بيحترم Retry-After. لما خدمة تقولك «استنّى 5 ثواني»، تجاهُلها بيخلّي حالتها أسوأ ويخلّيها ترفضك أكتر.
5. AddFallback هو التدهور الرشيق في صورة كود: بدل استثناء بيوصل للمستخدم، بنرجّع رد ناقص مع علامة stale، والواجهة تعرض «المخزون غير متاح مؤقتًا» والصفحة تفضل شغّالة.

وده بالظبط سلوك المستخدم الحقيقي: بيسكت شوية وبعدين بيطلب دفعة.
تطبيق .NET AddTokenBucketLimiter بإعدادات: TokenLimit (السعة) وTokensPerPeriod + ReplenishmentPeriod (المعدّل) وQueueLimit (كام طلب يستنى بدل ما يترفض فورًا).
فخ شائع ⚠️ سعة كبيرة أوي بتلغي الحماية: دلو بسعة 10,000 ومعدّل 100/s معناه إن عميل ساكت من ساعة يقدر يرمي 10 آلاف طلب في ثانية واحدة ⇒ ده بالظبط اللي كنت خايف منه.
القاعدة: السعة = 2–5× المعدّل في الثانية. يعني معدّل 100/s ⇒ سعة 200–500.
إمتى تستخدمه الخيار الافتراضي لـ APIs العامة. هو اللي بتستخدمه Stripe وGitHub وأغلب المنصات، لأنه بيحترم سلوك المستخدم الطبيعي وفي نفس الوقت بيمنع الاستهلاك المستمر الزائد.
Leaky Bucket الدلو المثقوب
التعريف الدقيق طابور بحجم ثابت، بيخرج منه طلب واحد كل فترة ثابتة مهما كان الداخل. الطلبات الزيادة بتستنى في الطابور، ولو الطابور اتملى بتترفض.
الفرق الجوهري عن دلو الرموز: الخروج منتظم تمامًا — مفيش انفجار خالص.
تشبيه 💧 دلو تحته خرم صغير. صبّ فيه مياه بأي سرعة — النقط اللي بتخرج ثابتة دايمًا. ولو صبّيت أكتر من اللازم، الدلو بيطفح والزيادة بتضيع.
تطبيق .NET مش موجود بالاسم ده في AddRateLimiter، لكن AddConcurrencyLimiter مع QueueLimit بيدّي نفس السلوك تقريبًا: خروج منتظم مع طابور محدود. وهو النمط المستخدم في Backpressure على المستهلكين.
فخ شائع ⚠️ الطابور بيضيف زمن انتظار للمستخدم. طلب دخل الطابور ورا 200 طلب هيستنى فترة طويلة وبعدها يتنفّذ — والمستخدم غالبًا يكون قفل الصفحة أصلاً.
ولذلك: لو الطابور طويل، الرفض السريع أرحم من الانتظار.
إمتى تستخدمه لما يكون المستهلِك حسّاس للمعدّل مش للعدد: الكتابة على قاعدة بيانات ليها سقف IOPS، أو النداء على API طرف تالت بيحظرك لو تجاوزت، أو إرسال إيميلات/رسائل بمعدّل مسموح.

Fixed Window · Sliding Window Log · Sliding Window Counter

التلاتة بيحاولوا يعدّوا الطلبات في فترة — والفرق بينهم في الدقة والذاكرة.

01

Fixed Window

عدّاد واحد بيتصفّر كل فترة (كل دقيقة مثلاً).
ميزته: أرخص حاجة ممكنة — رقم واحد في الذاكرة.
عيبه القاتل: مشكلة الحدود.

الحد = 100/دقيقة 12:00:59 → 100 طلب ✔ 12:01:00 → 100 طلب ✔ الفعلي في ثانيتين = 200 ⚠️
02

Sliding Window Log

بيخزّن توقيت كل طلب في قائمة، وبيمسح اللي أقدم من النافذة، وبيعدّ الباقي.
ميزته: دقة مثالية — مفيش أي مشكلة حدود.
عيبه: الذاكرة بتكبر مع عدد الطلبات.

الذاكرة = O(عدد الطلبات) مليون مستخدم × 100 = 100M طابع زمني ≈ 800 MB لمجرد العد!
03

Sliding Window Counter

الحل الوسط الذكي: عدّادين (النافذة الحالية والسابقة) + وزن حسب موقعك في النافذة.
ميزته: دقة قريبة من المثالي بذاكرة ثابتة.
عيبه: تقريب — بيفترض توزيع منتظم.

count = cur + prev × overlap مثال 30% في النافذة = 30 + 90 × 0.7 = 93
مثال محلول 5: نفس الانفجار — خمس خوارزميات — خمس نتايج

Program.csC# / .NET 9
builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    // ═══ 1) دلو رموز — للـ API العام (بيسمح بانفجار محدود) ═══
    options.AddTokenBucketLimiter("public-api", o =>
    {
        o.TokenLimit          = 300;   // سعة الدلو = أقصى انفجار
        o.TokensPerPeriod     = 100;   // بيتجدّد 100 رمز
        o.ReplenishmentPeriod = TimeSpan.FromSeconds(1); // كل ثانية ⇒ 100/s مستدام
        o.QueueLimit          = 0;     // ارفض فورًا بدل ما تستنّي
        o.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        o.AutoReplenishment   = true;
    });

    // ═══ 2) نافذة منزلقة — لتسجيل الدخول (حماية من التخمين) ═══
    options.AddSlidingWindowLimiter("login", o =>
    {
        o.PermitLimit     = 10;  // 10 محاولات
        o.Window          = TimeSpan.FromMinutes(5);  // كل 5 دقايق
        o.SegmentsPerWindow = 5; // النافذة مقسّمة 5 شرائح × دقيقة
        o.QueueLimit      = 0;
    });

    // ═══ 3) محدّد مقسّم — حد مستقل لكل مستأجر ═══
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(
        httpContext =>
    {
        // المفتاح: المستأجر لو مسجّل، وإلا عنوان العميل
        var tenant = httpContext.User.FindFirst("tenant_id")?.Value;

        if (tenant is not null)
        {
            // المستأجر المدفوع بياخد حصة أعلى — الأعمال بتحدّد الحدود مش التقنية
            var isPremium = httpContext.User.HasClaim("plan", "premium");

            return RateLimitPartition.GetTokenBucketLimiter(
                partitionKey: $"tenant:{tenant}",
                factory: _ => new TokenBucketRateLimiterOptions
                {
                    TokenLimit          = isPremium ? 2000 : 300,
                    TokensPerPeriod     = isPremium ? 500  : 100,
                    ReplenishmentPeriod = TimeSpan.FromSeconds(1),
                    QueueLimit          = 0,
                    AutoReplenishment   = true
                });
        }

        // المجهولون: حد أقل بكتير، مقسّم بعنوان العميل
        var ip = httpContext.Connection.RemoteIpAddress?.ToString() ?? "unknown";
        return RateLimitPartition.GetFixedWindowLimiter(
            partitionKey: $"ip:{ip}",
            factory: _ => new FixedWindowRateLimiterOptions
            {
                PermitLimit = 30,
                Window      = TimeSpan.FromMinutes(1)
            });
    });

    // ═══ 4) رد مفيد بدل 429 فاضية — قول له يستنّى قد إيه ═══
    options.OnRejected = async (ctx, ct) =>
    {
        if (ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retry))
            ctx.HttpContext.Response.Headers.RetryAfter =
                ((int)retry.TotalSeconds).ToString();

        await ctx.HttpContext.Response.WriteAsJsonAsync(new
        {
            error = "rate_limited",
            message = "تجاوزت الحد المسموح. حاول تاني بعد شوية."
        }, ct);
    };
});

var app = builder.Build();
app.UseRateLimiter();

app.MapPost("/auth/login", LoginHandler).RequireRateLimiting("login");
app.MapGet("/api/products", ListHandler).RequireRateLimiting("public-api");
أهم القرارات في الكود ده 1. TokenLimit = 300 مع TokensPerPeriod = 100/s ⇒ 100 طلب/ثانية مستدام، مع سماح بانفجار لحد 300 لو العميل كان ساكت. النسبة 3× هي المدى العملي المتوازن.
2. QueueLimit = 0 — ما نستنّاش، نرفض فورًا. الانتظار في محدّد المعدّل بيحوّله لطابور، والطابور هو المشكلة اللي بنهرب منها أصلاً.
3. SegmentsPerWindow = 5 في النافذة المنزلقة معناها: النافذة (5 دقايق) مقسّمة لـ 5 شرائح دقيقة، والعدّاد بيتحرّك شريحة بشريحة. ده اللي بيمنع مشكلة الحدود بتاعت النافذة الثابتة.
4. PartitionedRateLimiter هو لب الموضوع في الأنظمة متعددة المستأجرين: كل مستأجر عنده دلوه الخاص، فمستأجر شرِه ما بيأثرش على غيره. وربط الحد بخطة الاشتراك بيحوّل الحماية التقنية لميزة تجارية.
5. OnRejected مع Retry-After — من غيرها العميل هيعيد فورًا وهيفضل يترفض. مع الترويسة، مكتبات الإعادة (زي Polly) بتحترمها تلقائيًا وبتهدّي.

ملاحظة للتوسّع الأفقي: المحدّدات دي كلها في ذاكرة النسخة. مع 5 نسخ الحد الفعلي بقى 5×. لو محتاج دقة، نفّذ العدّاد في Redis بسكربت Lua ذرّي — أو اقبل التقريب واضبط الحد على الحد ÷ عدد النسخ.

التحمّل والتكرار والتبديل عند الفشل

تلات مصطلحات بيتقالوا مع بعض دايمًا — وكل واحد بيوصف حاجة مختلفة تمامًا.

🛡️

Fault Tolerance

الهدف / الصفة. قدرة النظام إنه يفضل شغّال وهو فيه أعطال.
ده الوصف اللي عايز توصله، مش أداة.

📑

Redundancy

الوسيلة. إن يكون عندك أكتر من نسخة من كل مكوّن حرج.
من غير تكرار، مفيش تحمّل أعطال — دي أبسط معادلة في الباب ده.

🔀

Failover

الآلية. عملية تحويل الحمل من النسخة المعطوبة للسليمة.
التكرار من غير تبديل تلقائي = نسخة احتياطية بتتفرّج على النظام وهو واقع.

العلاقة بينهم في جملة Redundancy (نسخ زيادة) + Failover (تحويل تلقائي) = Fault Tolerance (نظام بيتحمّل الأعطال).
لو ناقصك واحد منهم، النتيجة مش بتتحقق.
⚖️⚖️

Active-Active

كل النسخ بتخدم ترافيك في نفس الوقت.

  • مفيش موارد نايمة — بتدفع وبتستفيد من كل حاجة.
  • التبديل عند الفشل شبه فوري (ثواني) — الترافيك بيتوزّع على الباقي.
  • بتختبر النسخ كل يوم بالترافيك الحقيقي.
  • لازم كل نسخة تشتغل على نفس البيانات ⇒ مشكلة اتساق.
  • لازم تشغّل على ≤ 50% استغلال لو عندك موقعين (عشان واحد يستحمل الحمل كله).
  • الكتابة المتزامنة على مناطق بعيدة بتضيف زمن حقيقي.
VS
😴

Active-Passive

نسخة بتشتغل، والتانية مستنية جاهزة.

  • أبسط بكتير — مفيش تعقيد اتساق ولا كتابة موزّعة.
  • مناسب للمكوّنات اللي طبيعتها كاتب واحد (قواعد بيانات علائقية).
  • بتدفع في مورد مش بتستخدمه — تكلفة مضاعفة بلا إنتاجية.
  • التبديل بياخد وقت (30s – 5min) وبيبقى فيه انقطاع.
  • الخطر الحقيقي: النسخة الاحتياطية مش متأكد إنها شغّالة — لأنها ما بتاخدش ترافيك أبدًا. أشهر سبب لفشل التبديل.
⏱️
مقياسان لازم تعرفهم في التبديل RTO (Recovery Time Objective) = قد إيه ممكن نفضل واقعين؟
RPO (Recovery Point Objective) = كام بيانات مسموح تضيع؟

مثال: RTO = 5 دقايق وRPO = 0 ⇒ نسخ متزامن إجباري وتبديل تلقائي.
RTO = 4 ساعات وRPO = 1 ساعة ⇒ نسخة احتياطية كل ساعة واستعادة يدوية كفاية. الرقمين دول بيحدّدوا التكلفة أكتر من أي حاجة تانية.

التدهور الرشيق والضغط العكسي

الأول بيقول «قدّم أقل بدل ما تقع»، والتاني بيقول «ما تقبلش شغل أكتر من طاقتك».

Graceful Degradation التدهور الرشيق
التعريف الدقيق إن النظام يفقد ميزات ثانوية عند الضغط أو العطل، ويحافظ على الوظيفة الأساسية شغّالة — بدل ما يفشل كليًا.
تشبيه ✈️ الطيارة لما بتفقد محرك: بتقفل التكييف والترفيه وشحن الأجهزة، وبتحافظ على أنظمة التحكّم والملاحة.
محدش بيقول «الطيارة اتعطّلت» — بيقولوا «رحلة أقل راحة».
إزاي تطبّقه عمليًا — سلّم التدهور رتّب مميزاتك من الأهم للأقل، ونفّذ التنازل بالترتيب:
المستوى 0 (طبيعي): كل حاجة شغّالة.
المستوى 1: اقفل التوصيات والمنتجات المشابهة، اعرض بيانات من الكاش حتى لو قديمة.
المستوى 2: اقفل البحث المعقّد وخلّيه بحث بسيط، اقفل التقارير والتصدير.
المستوى 3: قراءة فقط — الشراء والتسجيل شغّالين، التعديلات مقفولة.
المستوى 4: صفحة ثابتة من الـ CDN بتقول إحنا شغالين على المشكلة.
الترتيب ده لازم يتكتب قبل الأزمة — وقت الأزمة محدش هيقدر يقرّر.
فخ شائع ⚠️ تدهور صامت: الميزة اتقفلت ومحدش عرف، لا المستخدم ولا الفريق. فبتفضل مقفولة أسابيع.
الصح: كل تنازل يبان للمستخدم برسالة واضحة، وللفريق بمقياس ولوج وتنبيه.

Backpressure الضغط العكسي
التعريف الدقيق إشارة بترجع من المستهلِك للمنتِج بتقول «بطّأ، أنا مش لاحق».
الفكرة الجوهرية: لما تكون مش قادر، ارفض بسرعة بدل ما تقبل وتخزّن في طابور — لأن الطابور بيأجّل المشكلة وبيكبّرها مش بيحلها.
تشبيه 🍽️ مطعم زحمة. عنده اختيارين:
(أ) يقبل كل الطلبات ويحطها في طابور ⇒ الزبون بيستنى ساعة، والأكل بيبرد، والكل بيمشي زعلان.
(ب) يقول «مفيش أماكن دلوقتي، تعال بعد نص ساعة» ⇒ الزبون زعلان دقيقة بس يوم كويس.
الضغط العكسي هو الاختيار (ب).

// خدمة خلفية بقناة محدودة (ضغط عكسي) + إغلاق رشيق كامل
public sealed class IngestWorker : BackgroundService
{
    private readonly Channel<Event> _channel;
    private readonly IHostApplicationLifetime _lifetime;
    private readonly IReadinessState _readiness;
    private readonly ILogger<IngestWorker> _log;

    public IngestWorker(IHostApplicationLifetime lifetime,
        IReadinessState readiness, ILogger<IngestWorker> log)
    {
        _lifetime = lifetime;
        _readiness = readiness;
        _log = log;

        // قناة محدودة: لما تمتلي، الكاتب بيستنى ⇒ ضغط عكسي حقيقي
        // Unbounded هنا كان هيبقى تسريب ذاكرة مضمون
        _channel = Channel.CreateBounded<Event>(new BoundedChannelOptions(1000)
        {
            FullMode = BoundedChannelFullMode.Wait,
            SingleReader = false
        });
    }

    public ValueTask EnqueueAsync(Event e, CancellationToken ct)
        => _channel.Writer.WriteAsync(e, ct);   // بيستنى لو مليانة

    protected override async Task ExecuteAsync(CancellationToken stopping)
    {
        // ═══ 1) عند SIGTERM: اقلب readiness لـ false فورًا ═══
        // الموزّع هيشيلنا من الدورة قبل ما نبدأ نقفل ⇒ صفر طلبات ضايعة
        _lifetime.ApplicationStopping.Register(() =>
        {
            _readiness.IsReady = false;
            _log.LogInformation("بدأ الإغلاق — اتشلنا من الموزّع");
        });

        // ═══ 2) المعالجة الطبيعية ═══
        try
        {
            await foreach (var e in _channel.Reader.ReadAllAsync(stopping))
            {
                await ProcessAsync(e, stopping);
            }
        }
        catch (OperationCanceledException) { /* إغلاق متوقّع */ }

        // ═══ 3) تصريف: خلّص اللي في القناة قبل الخروج ═══
        _channel.Writer.TryComplete();
        using var drain = new CancellationTokenSource(TimeSpan.FromSeconds(20));

        var left = 0;
        await foreach (var e in _channel.Reader.ReadAllAsync(drain.Token))
        {
            await ProcessAsync(e, drain.Token);
            left++;
        }
        _log.LogInformation("اتصرّف {N} حدث قبل الإغلاق", left);
    }
}

Amdahl's Law — سقف التسريع بالتوازي

القانون اللي بيفسّر ليه إضافة سيرفرات بتقف عن الفايدة عند نقطة معيّنة.

// ═══ صيغة أمدال ═══ Speedup(N) = 1 / ( (1 − p) + p/N ) // ═══ لو 95% من الشغل يتوازى (p = 0.95) ═══ N = 2 → 1.90× N = 10 → 6.90× N = 100 → 16.8× ← 100 سيرفر مقابل 17 ضعف بس N = 1000 → 19.6× N = ∞ → 20× ← السقف المطلق مهما ضفت // ═══ السقف = 1 / (1 − p) ═══ p = 0.50 → السقف 2× p = 0.90 → السقف 10× p = 0.99 → السقف 100×
Speedup(N) = 1 / ((1 − p) + p/N)
أربع رموز — والمعنى العملي أهم من الصيغة
p
نسبة الشغل القابل للتوازي (من 0 لـ 1).
في نظام ويب: كل الأجزاء اللي كل طلب بيعملها لوحده — تحليل الطلب، الحسابات، بناء الرد.
1 − p
الجزء التسلسلي — اللي لازم يتنفّذ واحد ورا التاني مهما كان عندك سيرفرات.
في نظام ويب ده: الكتابة على قاعدة بيانات واحدة، والأقفال، والتسلسلات (sequences)، والمعاملات الموزّعة، وأي مورد مشترك.
ده «الشيف الواحد» في المطبخ اللي فيه 20 مساعد.
p / N
الجزء المتوازي بعد ما اتقسّم على N عامل — وده الجزء الوحيد اللي بيقل لما تضيف موارد.
لاحظ: كل ما N كبر، الحد ده بيقرّب من الصفر — وساعتها الكسر كله بيبقى 1/(1−p) وخلاص.
1 / (1 − p)
السقف المطلق. لو 5% من شغلك تسلسلي، أقصى تسريع ممكن = 1/0.05 = 20 ضعف — حتى لو عندك مليون سيرفر.
ده مش رأي ولا تقدير، ده قيد رياضي.
القانون بيقول: الجزء اللي مش بيتوازى هو اللي بيحدّد سقفك — مش عدد السيرفرات. عشان كده تقليل الجزء التسلسلي من 5% لـ 1% بيرفع سقفك من 20× لـ 100×، وده مكسب مستحيل توصله بشراء عتاد.
🎯
إزاي تحوّل ده لقرارات في نظامك بكرة كل بند هنا هو «جزء تسلسلي» بتشيله:
1. قفل عام على جدول ⇒ استبدله بتفاؤلي (Optimistic Concurrency بـ rowversion).
2. كل الكتابة على قاعدة واحدة ⇒ قسّم البيانات (Sharding) أو استخدم طابور يجمّع الكتابات.
3. توليد أرقام تسلسلية مركزي ⇒ ULID أو Snowflake ID يتولّد محليًا في كل نسخة.
4. جلسة مشتركة على مخزن واحد ⇒ توكن موقّع عند العميل.

كل واحدة من دول بتنقص (1−p) — وبالتالي بترفع السقف اللي كل استثماراتك في العتاد بتصطدم بيه.
القانون 02

Universal Scalability Law — لما الزيادة تبقى ضارّة

أمدال بيقول «فيه سقف». الـ USL بيقول حاجة أسوأ: بعد نقطة معيّنة، الزيادة بتقلّل الإنتاجية فعليًا.

// ═══ صيغة USL ═══ C(N) = N / ( 1 + α(N−1) + βN(N−1) ) // ═══ مثال: α = 0.03 (تنافس 3%) · β = 0.0001 (تماسك) ═══ N = 1 → 1.00× N = 10 → 7.87× N = 30 → 14.9× N = 57 → 17.0× ← الذروة N = 100 → 16.4× ← أقل من الذروة! N = 200 → 12.9× ← ضفنا 143 سيرفر وخسرنا 24% // ═══ نقطة الذروة ═══ N* = √( (1 − α) / β ) = ≈ 57 سيرفر
C(N) = N / (1 + α(N−1) + βN(N−1))
حدّين بس زيادة عن أمدال — وهما اللي بيفسّروا كل حاجة
N
عدد العمال — سيرفرات، أو أنوية، أو خيوط، أو اتصالات متزامنة.
في البسط لوحده يعني: «لو مفيش أي احتكاك، الإنتاجية بتتضاعف مع العدد» (المثالي).
α (alpha)
معامل التنافس — Contention. ده هو نفسه الجزء التسلسلي عند أمدال: الانتظار على مورد مشترك (قفل، اتصال، قاعدة بيانات).
بيكبر خطّيًا مع N: كل عامل جديد بيستنى في نفس الطابور.
تشبيه: 50 شيف بيستنوا دورهم على فرن واحد.
β (beta)
معامل التماسك — Coherency. وده الجزء الجديد اللي أمدال ما حسبوش.
ده تكلفة إبقاء كل العمال متفقين على نفس الحالة: مزامنة الكاش، اتفاق العقد، إبطال البيانات، نبضات الصحة.
بيكبر تربيعيًا — لأن عدد أزواج التواصل بين N عقدة = N(N−1)/2.
